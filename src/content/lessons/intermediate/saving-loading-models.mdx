**Saving a model** means writing its learned numbers to a file so that it can make predictions later, be shared, or continue training after an interruption. In <Term slug="pytorch" /> the recommended unit to save is the <Term slug="state-dict" />, a dictionary that maps every layer's parameter names to their tensors.<Cite id="pt-save-load" /> A full **checkpoint** adds the optimizer's state and the epoch so that training can resume exactly where it stopped.<Cite id="pt-serialization" />

## The state_dict

Every `nn.Module` has a `state_dict()` method that returns an ordered dictionary of its parameters and buffers.<Cite id="pt-module" /> For `nn.Sequential(nn.Linear(4, 16), nn.ReLU(), nn.Linear(16, 1))` the keys are `0.weight`, `0.bias`, `2.weight` and `2.bias`; the ReLU at position 1 has no parameters, so it has no entry. Buffers that are not trained but still matter, such as the running statistics of <Term slug="batch-normalization" />, are included too.<Cite id="pt-save-load" />

Saving and loading take one line each:

```python
torch.save(model.state_dict(), "weights.pt")           # save
model = MyModel()                                       # rebuild the same architecture in code
model.load_state_dict(torch.load("weights.pt", weights_only=True))
model.eval()                                            # inference mode for dropout/BatchNorm
```

The file stores only numbers, not the model's code. You recreate the architecture from your own class and pour the numbers into it, so the class must match: a missing or renamed layer raises an error listing the missing and unexpected keys.<Cite id="pt-module" /> Read that list carefully: it usually points straight at the layer that changed. When you deliberately reuse only part of a network, for example a trained body under a new output layer, `load_state_dict(..., strict=False)` loads the matching keys and returns the ones it skipped.<Cite id="pt-module" /> PyTorch files conventionally end in `.pt` or `.pth`; the extension is only a convention.<Cite id="pt-save-load" />

<Analogy breaks="A recipe card is useful without its cake; a state_dict is useless without the exact model code it was made from.">
A state_dict is like the settings sheet for a mixing desk: it lists every knob's position, but you still need the same desk to set them on.
</Analogy>

### Why not save the whole model?

`torch.save(model, path)` also works, but it pickles the model object, which records the module path of its class. Renaming a file or moving the class later can make the saved model impossible to load.<Cite id="pt-save-load" /> Saving the state_dict keeps the file independent of how your code is organized, which is why the PyTorch tutorials recommend it.

## Full checkpoints for resuming

To continue training later, the weights are not enough. The optimizer has its own state: for Adam, two running averages per parameter and a step count, which shape every future update.<Cite id="kingma2014" /> A checkpoint is therefore an ordinary dictionary holding everything the loop needs:<Cite id="pt-serialization" />

```python
torch.save({
    "epoch": epoch,
    "model_state_dict": model.state_dict(),
    "optimizer_state_dict": optimizer.state_dict(),
    "loss": loss,
}, "checkpoint.pt")
```

To resume, rebuild the model and the optimizer exactly as before, load each state into its object, and start the loop at the saved epoch.<Cite id="pt-save-load" /> If you use a learning-rate scheduler, save its `state_dict()` as well. Common practice is to save a checkpoint every epoch (or every few minutes on long runs) and to keep a separate copy of the best one according to the validation score, which is how the companion script of [the training loop lesson](/course/intermediate/training-loop/) implements early stopping.

<Callout type="tip">
Because a checkpoint holds the optimizer's extra numbers, it is about three times larger than the weights when training with Adam. Share the small state_dict for inference; keep the checkpoint for yourself.
</Callout>

## Loading safely: weights_only and map_location

`torch.load` is built on Python's `pickle`, and unpickling can execute arbitrary code embedded in the file.<Cite id="py-pickle" /> Since PyTorch 2.6 the default is `weights_only=True`, which restricts loading to tensors, numbers, strings and plain containers such as dicts and lists.<Cite id="pt-load" /> State dicts and checkpoint dicts like the one above load fine under this restriction. Never switch it off for a file from a source you do not trust.<Cite id="pt-serialization" />

A tensor remembers the device it was saved from. A checkpoint written on a GPU machine fails to load on a CPU-only laptop unless you pass `map_location="cpu"`, which moves every tensor to the CPU while loading.<Cite id="pt-load" /> Writing `map_location="cpu"` always is harmless, and the course's companion code does so.

<Callout type="pitfall">
After loading weights for prediction, call `model.eval()` and wrap predictions in `torch.no_grad()`. Forgetting `eval()` leaves dropout active, so the same input gives different, worse answers each time.
</Callout>

## Reproducibility

A resumed run only matches an uninterrupted one if the random numbers match too. Fixing the seed with `torch.manual_seed(0)` at the start makes weight initialization and shuffling repeatable on the same machine and PyTorch version; the PyTorch notes warn that results are not guaranteed to be identical across releases, platforms or CPU and GPU.<Cite id="pt-randomness" /> For long projects, save the random-generator state in the checkpoint too (`torch.get_rng_state()`), or accept that the data order after resuming will differ slightly.

## Summary

- Save the `state_dict()`, not the whole model; rebuild the class in code and call `load_state_dict`.
- A resumable checkpoint is a dict with the model and optimizer state_dicts, the epoch and anything else the loop needs.
- `torch.load` uses pickle: keep `weights_only=True` and never load untrusted full-model files.
- Use `map_location="cpu"` to load GPU checkpoints on any machine.
- Call `model.eval()` and `torch.no_grad()` before predicting with loaded weights.
