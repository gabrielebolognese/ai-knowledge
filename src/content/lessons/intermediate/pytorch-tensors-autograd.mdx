A **tensor** is PyTorch's basic data type: a multi-dimensional array of numbers with a shape, a data type and a device, much like a NumPy array.<Cite id="pt-tensors" /> PyTorch adds two things NumPy lacks: tensors can live on a GPU, and they can record the operations applied to them so that gradients are computed automatically, a feature called **autograd**.<Cite id="pt-autograd" /> Together they replace the hand-derived gradients of the [backpropagation lesson](/course/intermediate/backpropagation/) with one line of code.

## Tensors

A tensor can hold a single number (a scalar), a vector, a matrix or a higher-dimensional block, such as a batch of colour images with shape (batch, channels, height, width).<Cite id="pt-tensors" /> The word is used loosely in machine learning: it simply means an n-dimensional array, see <Term slug="tensor" />. Every tensor carries three attributes worth checking whenever something goes wrong:<Cite id="pt-tensor-api" />

| Attribute | Example | Meaning |
|---|---|---|
| `t.shape` | `torch.Size([2, 3])` | number of entries along each dimension |
| `t.dtype` | `torch.float32` | the number type; floats are the default for decimals |
| `t.device` | `cpu` | where the data lives: `cpu`, `cuda` or `mps` |

Tensors are created from Python lists with `torch.tensor(...)`, or filled with `torch.zeros`, `torch.ones`, `torch.rand` and `torch.arange`. Arithmetic works element by element with the same broadcasting rules as NumPy, `@` is matrix multiplication, and reductions such as `t.sum(dim=0)` collapse one dimension.<Cite id="pt-tensors" /> A tensor moves between devices with `t.to("cuda")`, and every tensor in one operation must be on the same device.<Cite id="pt-tensor-api" /> If you have no GPU, everything in this track runs on the CPU, or on a free [Google Colab](https://colab.research.google.com/) GPU (see <Term slug="google-colab" />).

### NumPy and PyTorch

`torch.from_numpy(a)` turns a NumPy array into a tensor **without copying**: the two share memory, so changing one changes the other. `t.numpy()` goes back the same way for CPU tensors.<Cite id="pt-tensors" /> By contrast, `torch.tensor(a)` always makes a copy.<Cite id="pt-tensor-api" />

<Callout type="pitfall">
NumPy's default float type is 64-bit, PyTorch's is 32-bit. A tensor created with `torch.from_numpy` keeps `float64`, and multiplying it with the `float32` weights of a model raises a dtype error. Convert with `.float()`.
</Callout>

## Autograd: gradients for free

Setting `requires_grad=True` on a tensor tells PyTorch to record every operation that uses it. As your code runs, PyTorch builds a <Term slug="computational-graph" /> behind the scenes; each result remembers the function that created it in its `grad_fn` attribute.<Cite id="pt-autograd" /> Calling `.backward()` on a scalar result, usually the loss, walks that graph in reverse and stores $\partial L / \partial w$ in the `.grad` attribute of every *leaf* tensor that required gradients, that is, every tensor you created yourself rather than computed.<Cite id="pt-autograd-notes" />

This is reverse-mode <Term slug="automatic-differentiation" />, the same algorithm as <Term slug="backpropagation" />. PyTorch builds the graph anew on every forward pass ("define-by-run"), which is why ordinary Python `if` statements and loops can change the network from one call to the next.<Cite id="paszke2019" />

<Analogy breaks="A flight recorder is read only after something goes wrong; autograd's tape is read on every training step, and it is thrown away after each use.">
Autograd works like a flight recorder. While the forward pass runs it notes every operation in order; `.backward()` plays the recording in reverse to work out how each input affected the result.
</Analogy>

## Gradients accumulate

PyTorch does not overwrite `.grad` when you call `.backward()` again; it **adds** the new gradient to the old one.<Cite id="pt-autograd" /> This is deliberate. It makes forks in the graph work (gradients from several paths must be summed), and it lets you accumulate gradients over several small batches before one update.<Cite id="pt-autograd-notes" />

In a training loop you almost always want the gradient of the *current* batch only, so you zero the gradients once per iteration, usually with `optimizer.zero_grad()`.<Cite id="pt-autograd" /> The [training loop lesson](/course/intermediate/training-loop/) puts this in its place.

## Switching tracking off

Recording costs memory and time, and many computations do not need gradients: evaluating a model, plotting predictions or applying a manual weight update. Wrap them in `with torch.no_grad():` and PyTorch records nothing inside the block; results then have `requires_grad=False`.<Cite id="pt-no-grad" /> The stricter `torch.inference_mode()` does the same with a little less overhead, for code that will never need gradients.<Cite id="pt-autograd-notes" />

To cut a single tensor out of the graph, use `t.detach()`. It returns a tensor that shares the same data but has no history, which is useful for logging a value or for stopping gradients from flowing into part of a model.<Cite id="pt-autograd" /> Another everyday use is `loss.item()`, which turns a one-element tensor into a plain Python number for printing; keeping the tensor itself in a list would keep its whole graph alive.<Cite id="pt-tensor-api" />

Two more rules explain common error messages. `.backward()` needs a scalar unless you pass a `gradient` argument, because "the gradient of a vector" is not one number per parameter.<Cite id="pt-autograd" /> And PyTorch frees the graph after `.backward()` to save memory, so calling it twice on the same result fails unless the first call used `retain_graph=True`.<Cite id="pt-autograd-notes" />

## Summary

- A tensor is an n-dimensional array with a shape, a dtype and a device; check all three when debugging.
- `torch.from_numpy` shares memory with NumPy, while `torch.tensor` copies; watch for `float64` versus `float32`.
- `requires_grad=True` plus `.backward()` fills `.grad` with exact gradients, the same numbers backpropagation gives by hand.
- Gradients accumulate, so zero them once per training step.
- Use `torch.no_grad()` for evaluation, `.detach()` for single tensors and `.item()` for logging.
