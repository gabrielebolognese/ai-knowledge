The **training loop** is the piece of code that repeatedly shows a model a batch of examples, measures how wrong it is, and nudges its weights to be a little less wrong. In <Term slug="pytorch" /> it is written by hand, which makes every step visible and easy to change.<Cite id="pt-optimization" /> Almost every model in this course, from digit recognisers to the chess evaluator, trains with the same few lines.<Cite id="pt-intro" />

## The five lines

For each mini-batch of inputs `X` and labels `y`, a PyTorch training step does five things in a fixed order:<Cite id="pt-optimization" />

1. **Forward pass**: `logits = model(X)` runs the inputs through the network.
2. **Loss**: `loss = loss_fn(logits, y)` compares predictions with the labels and returns a single number, the <Term slug="loss-function" />.
3. **Clear old gradients**: `optimizer.zero_grad()` sets every parameter's `.grad` back to zero.
4. **Backward pass**: `loss.backward()` runs backpropagation and stores $\partial L / \partial w$ in each parameter's `.grad`.<Cite id="d2l-autograd" />
5. **Update**: `optimizer.step()` changes every parameter using its gradient, for plain SGD $w \leftarrow w - \eta \cdot \text{grad}$.

Step 3 exists because PyTorch *adds* new gradients to whatever is already stored in `.grad` instead of overwriting it. That is useful for advanced tricks such as accumulating gradients over several small batches, but if you forget to clear them, each step uses the sum of all past gradients and training goes wrong.<Cite id="pt-optimization" />

<Analogy breaks="A student remembers past mistakes; the model keeps nothing between steps except its weights and the optimizer's running averages.">
The loop is like a practice routine with flash cards: attempt the stack (forward), get graded (loss), wipe last round's notes (zero_grad), work out what went wrong (backward), adjust (step). One lap through the whole deck is an epoch.
</Analogy>

## Epochs, iterations and batches

One **iteration** (or step) processes one batch. One <Term slug="epoch" /> is a full pass over the training data, so with 55,000 images and a batch size of 64 an epoch has 860 iterations. The `DataLoader` with `shuffle=True` deals the batches in a new random order every epoch, so the model never sees the same sequence twice.<Cite id="pt-intro" />

Log the **average** training loss over each epoch rather than the last batch's loss: a single batch is noisy, and the average shows the trend. Call `loss.item()` when you log it. The `loss` object is a tensor attached to the computation graph, and storing it in a list keeps every graph alive in memory.<Cite id="pt-optimization" />

## Loss functions take logits

For classification, the last layer outputs one raw score per class, called <Term slug="logits" />. `nn.CrossEntropyLoss` expects exactly these: it applies a log-<Term slug="softmax" /> internally and then computes the <Term slug="cross-entropy" /> against **integer class labels** (`dtype=torch.long`, shape `(N,)`).<Cite id="pt-crossentropy" /> Two common mistakes follow from this:

- Adding `nn.Softmax` as the model's last layer, then using `CrossEntropyLoss`. Softmax is applied twice, the gradients shrink, and training is slow or stalls.
- Passing float or one-hot labels where class indices are expected (the loss accepts probabilities as targets only in a specific form, which is rarely what you want).

Apply softmax yourself only when you need probabilities to display, never before the loss.<Cite id="pt-crossentropy" />

## Validation: eval mode and no_grad

After each epoch, measure the model on a <Term slug="validation-set">validation set</Term>, data it does not train on. Two calls make this pass correct and cheap:<Cite id="pt-optimization" />

- `model.eval()` switches layers that behave differently at inference time, such as <Term slug="dropout" /> and <Term slug="batch-normalization" />, into evaluation mode. `model.train()` switches them back.<Cite id="pt-module" />
- `with torch.no_grad():` tells autograd not to record operations, which saves memory and time because no backward pass will follow.<Cite id="pt-no-grad" />

They are independent: `eval()` does not turn off gradients, and `no_grad()` does not change dropout. A validation pass needs both.

<Callout type="pitfall">
Forgetting `model.train()` at the start of the next epoch leaves dropout switched off for the rest of training. Put `model.train()` at the top of every epoch, not once before the loop.
</Callout>

## A complete run on MNIST

The companion script trains a 784 → 128 → 10 network on <Term slug="mnist" /> with the Adam optimizer at its usual starting learning rate of $10^{-3}$.<Cite id="kingma2014" /> torchvision downloads the data on the first run; the 60,000 training images are split into 55,000 for training and 5,000 for validation, and the official 10,000 test images are scored once at the end.<Cite id="tv-mnist" /> Before training, the validation loss should be close to $\ln 10 \approx 2.303$, the loss of a model that guesses uniformly among ten classes; a very different value points to a bug.

On a laptop CPU the run takes about a minute and prints:

| Stage | Train loss | Val loss | Val accuracy |
|---|---|---|---|
| Before training | – | 2.316 | 0.108 |
| Epoch 1 | 0.267 | 0.148 | 0.956 |
| Epoch 2 | 0.116 | 0.117 | 0.962 |
| Epoch 3 | 0.080 | 0.106 | 0.967 |

The best checkpoint then scores about **97.3%** on the test set. Exact digits vary slightly between PyTorch versions and machines, but the shape of the curve should match.<Cite id="pt-intro" /> The project lesson [MNIST baseline with an MLP](/course/project-digits-letters/mnist-mlp-baseline/) continues from here.

## Summary

- Every training step is forward, loss, `zero_grad()`, `backward()`, `step()`.
- PyTorch accumulates gradients, so clear them once per iteration.
- `CrossEntropyLoss` takes logits and integer labels; never put softmax before it.
- Validate with `model.eval()` and `torch.no_grad()`, then switch back with `model.train()`.
- A 784 → 128 → 10 MLP reaches about 97% on MNIST in three epochs on a CPU.
