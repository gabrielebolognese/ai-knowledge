In PyTorch a model is written as a subclass of **`nn.Module`**, and training data is wrapped in a **`Dataset`** that a **`DataLoader`** deals out in shuffled mini-batches.<Cite id="pt-model" /><Cite id="pt-data" /> These three classes keep the model, the data and the training code separate, so the same model can be trained on different data and the same data fed to different models. Every project in this course uses them.

## nn.Module: a model as a class

A module bundles layers, which hold the trainable parameters, with a `forward` method that says how an input flows through them.<Cite id="pt-module" /> The pattern is always the same:

1. subclass `nn.Module` and call `super().__init__()` first in `__init__`
2. create the layers in `__init__` and store them as attributes
3. write the computation in `forward(self, x)` and return the output.

Assigning a layer to `self` *registers* it: the module now knows about its parameters, moves them with `model.to(device)`, saves them in its `state_dict` and hands them to the optimizer through `model.parameters()`.<Cite id="pt-module" /> `nn.Linear(784, 128)` holds a weight of shape (128, 784) and a bias of 128 numbers, computes $xW^\top + b$, and starts with small random weights, so you do not need to initialise anything by hand.<Cite id="pt-linear" />

You run a module by *calling* it, `logits = model(x)`, not by calling `model.forward(x)`. The call goes through `nn.Module`'s machinery, which runs `forward` together with any registered hooks.<Cite id="pt-module" /> The output is raw scores, called logits, with no softmax: the loss function used for classification expects logits, as the training-loop lesson explains.<Cite id="pt-model" />

<Analogy breaks="LEGO pieces have no numbers inside them; every layer here carries weights that training will change.">
An `nn.Module` is like a LEGO baseplate: you snap layers onto it in `__init__`, and `forward` describes how the pieces connect. Modules can be snapped into bigger modules, just as small LEGO builds become parts of larger ones.
</Analogy>

### nn.Sequential for simple stacks

When the data simply flows through layers in order, `nn.Sequential` saves writing a class: `nn.Sequential(nn.Flatten(), nn.Linear(784, 128), nn.ReLU(), nn.Linear(128, 10))` builds the same network.<Cite id="pt-sequential" /> Write a subclass as soon as the forward pass needs anything more, such as two inputs, a skip connection or a branch.<Cite id="pt-model" />

### Counting and inspecting parameters

`model.parameters()` yields every trainable tensor, and `model.named_parameters()` adds their names.<Cite id="pt-module" /> Summing `p.numel()` over them counts the numbers to be learned; for this model it gives 101,770, the same total as the hand count in the multilayer perceptron lesson. Printing the model lists its layers, and the names (`hidden.weight`, `out.bias`) are the keys you will later see in saved checkpoints.

## Dataset: what one example is

A **map-style** `Dataset` answers two questions: how many examples there are, through `__len__`, and what example number `i` is, through `__getitem__`, which usually returns a pair (features, label).<Cite id="pt-data-api" /> Loading from disk, decoding images or applying transforms all happens inside `__getitem__`, one example at a time.<Cite id="pt-data" />

When the data already sits in tensors, `TensorDataset(x, y)` does the same job in one line: item `i` is simply `(x[i], y[i])`.<Cite id="pt-data-api" /> Ready-made datasets such as `torchvision.datasets.MNIST` follow the same contract, so they plug into the same code.<Cite id="pt-data" />

## DataLoader: dealing mini-batches

A `DataLoader` wraps a dataset and yields <Term slug="mini-batch">mini-batches</Term>. With `shuffle=True` it draws a fresh random order every <Term slug="epoch" />, fetches `batch_size` examples, and stacks them into batch tensors whose first dimension is the batch.<Cite id="pt-data" /> For the two-moons set with `batch_size=64`, each batch is a features tensor of shape (64, 2) and a label tensor of shape (64,).

  legend={[

    { symbol: 'B', meaning: 'batch size' },

>
  <Step tex="N / B = 1000 / 64 = \hl{15.625}" words="The data does not divide evenly into batches of 64." />
  <Step tex="15 \cdot 64 = 960, \quad 1000 - 960 = \hl{40}" words="Fifteen full batches, and 40 examples are left over." />
  <Step tex="\text{batches} = \lceil N / B \rceil = \hl{16}" words="By default the leftovers form a smaller last batch, so one epoch has 16 batches. drop_last=True would discard it and give 15." />
</MathSteps>

Shuffle the training data but not the validation or test data: the order of evaluation does not change the score, and a fixed order makes runs easier to compare.<Cite id="pt-data" /> If a model's loss falls suspiciously slowly, check `shuffle=True` first, because training on data sorted by label is a classic silent bug.

<Analogy breaks="A card dealer never changes the cards; a DataLoader can also transform each example, for example to augment images.">
A DataLoader is like a card dealer who shuffles the deck before each round and hands out stacks of 64 cards; one round through the whole deck is an epoch.
</Analogy>

## The num_workers pitfall on Windows

`num_workers` sets how many extra processes load data in the background. The default, 0, loads everything in the main process, which is simple and fast enough for in-memory data such as this lesson's.<Cite id="pt-data-api" /> Larger values help when `__getitem__` does slow work, such as reading and decoding image files.

On Windows, and on macOS, Python starts those worker processes with the *spawn* method, which launches a fresh interpreter and re-imports your script.<Cite id="py-multiprocessing" /> If the training code sits at the top level of the file, every worker would run it again and try to start workers of its own, and Python stops with an error about starting a process before "the bootstrapping phase" has finished. The fix is to put the code in a function and call it under `if __name__ == "__main__":`.<Cite id="pt-windows" /> The same guard matters on Linux with Python 3.14 or newer, where the default start method changed to *forkserver*, which also imports the main module.<Cite id="py-multiprocessing" />

<Callout type="tip">
Keep `num_workers=0` while you develop and debug: errors inside `__getitem__` then show a normal traceback. Raise it only when data loading is measurably the bottleneck, and always use the `__main__` guard.
</Callout>

## Summary

- A model is an `nn.Module` subclass: layers in `__init__`, computation in `forward`, and you call `model(x)`.
- Layers assigned to `self` are registered, so `model.parameters()` finds them; 784→128→10 has 101,770.
- `nn.Sequential` is a shortcut for plain stacks of layers.
- A `Dataset` defines `__len__` and `__getitem__`; a `DataLoader` shuffles it and stacks mini-batches, $\lceil N/B \rceil$ per epoch.
- With `num_workers > 0`, guard the script with `if __name__ == "__main__":`, which Windows and macOS need.
