**Initialization** is the choice of the random numbers a network's weights start from, and **normalization** layers rescale activations while the network runs. Both exist to keep the signal flowing through many layers at a sensible size: if activations or gradients shrink or grow at every layer, a deep network trains slowly or not at all.<Cite id="d2l-init" /> Good defaults, such as He initialization for ReLU networks and normalization layers, are a large part of why networks with dozens of layers became trainable.<Cite id="he2015-init" /><Cite id="ioffe2015" />

## Why the starting point matters

A layer multiplies its input by a weight matrix. Repeat that ten times and any consistent scaling compounds: a factor of 2 per layer becomes $2^{10} = 1024$, and a factor of 0.5 becomes about 0.001.<Cite id="d2l-init" /> Small activations lead to small gradients that barely move the early layers, and large ones overflow or saturate the activation functions. These are the [vanishing and exploding gradient problems](https://en.wikipedia.org/wiki/Vanishing_gradient_problem), described in detail by Glorot and Bengio for deep networks.<Cite id="glorot2010" /> See <Term slug="exploding-gradient" /> in the glossary.

The weights must also be **random**. If every weight in a layer started with the same value, every unit would compute the same output and get the same gradient, and the units would stay identical forever.<Cite id="d2l-init" />

<Analogy breaks="Guitar strings are tuned once by ear; a network's weights are then changed millions of times by training, and initialization only sets the first state.">
Initialization is like tuning a guitar before playing. If every string has the same pitch, no chord is possible; if strings are far too tight or too loose, the sound is distorted or silent.
</Analogy>

## Keeping the variance constant

The fix is to scale the random weights to the number of inputs. Here is the argument with numbers, for one unit $z = \sum_i w_i x_i$ whose inputs have variance 1.

  <Step tex="\text{Xavier: } \text{Var}(w) = \hl{\tfrac{2}{n_\text{in} + n_\text{out}}},\quad a = \sqrt{\tfrac{6}{n_\text{in}+n_\text{out}}}" words="Glorot and Bengio average the forward (n_in) and backward (n_out) conditions. **Xavier (Glorot) initialization** (2010) was derived for tanh and sigmoid units.<Cite id="glorot2010" /> **He (Kaiming) initialization** (2015) is the version for <Term slug="relu">ReLU</Term>; He and colleagues used it to train a 30-layer ReLU network from scratch.<Cite id="he2015-init" /> Both are in [`torch.nn.init`](https://docs.pytorch.org/docs/stable/nn.init.html), which also offers `calculate_gain('tanh')` (5/3) and similar correction factors for other activations.<Cite id="pt-init" />

### What PyTorch does by default

`nn.Linear` already initializes its weights uniformly in $\pm 1/\sqrt{n_\text{in}}$, a scaled-down Kaiming-uniform variant, so small networks rarely need changes.<Cite id="pt-linear" /> For deeper ReLU networks, set He initialization explicitly and start biases at zero:<Cite id="pt-init" />

```python
def init_weights(m):
    if isinstance(m, nn.Linear):
        nn.init.kaiming_normal_(m.weight, nonlinearity="relu")
        nn.init.zeros_(m.bias)

model.apply(init_weights)      # calls init_weights on every submodule
```

## Batch normalization

**Batch normalization** (Ioffe and Szegedy, 2015) normalizes each feature over the current mini-batch to mean 0 and standard deviation 1, then applies a learned scale $\gamma$ and shift $\beta$, so the network can undo the normalization where that helps.<Cite id="ioffe2015" /> It lets networks train with higher learning rates and has a mild regularizing effect.<Cite id="d2l-batchnorm" /> In PyTorch it is `nn.BatchNorm1d` for vectors and `nn.BatchNorm2d` for images (see <Term slug="batch-normalization" />).<Cite id="pt-batchnorm" />

  <Step tex="\hat x = \tfrac{x - \mu}{\sqrt{\sigma^2 + \epsilon}} = [\hl{-1.069, -0.535, 0, 1.604}]" words="Subtract the mean and divide by the standard deviation: mean 0, std 1." />

### Training mode versus evaluation mode

During training, BatchNorm uses the statistics of the current batch and also updates **running averages** of the mean and variance. In evaluation mode it uses those running averages instead, so a prediction does not depend on which other examples happen to share its batch.<Cite id="pt-batchnorm" /> This is why `model.eval()` matters. In the script below, after a single batch the running mean is only 0.3 (PyTorch moves it 10% of the way from 0 towards 3 per batch), so the same four inputs give quite different outputs in the two modes. After many batches the running values settle on the dataset's statistics.<Cite id="d2l-batchnorm" />

Why BatchNorm helps is still debated. Ioffe and Szegedy explained it as reducing "internal covariate shift", changes in each layer's input distribution during training.<Cite id="ioffe2015" /> Santurkar and colleagues later found that BatchNorm helps even when that shift is not reduced, and argued that it mainly makes the loss surface smoother.<Cite id="santurkar2018" /> It is safest to say that it reliably helps in practice and that the reasons are still being researched.

<Analogy breaks="A teacher curves grades once per exam; BatchNorm recomputes the curve for every mini-batch during training and switches to a fixed curve at evaluation time.">
BatchNorm resembles grading on a curve: each batch's raw scores are re-centred and rescaled before they are passed on, so the next layer always sees numbers on a familiar scale.
</Analogy>

## Layer normalization

**Layer normalization** (Ba, Kiros and Hinton, 2016) computes the same mean-and-variance normalization, but over the features of *each example* instead of over the batch.<Cite id="ba2016" /> It needs no batch statistics, so it behaves the same in training and evaluation, works with a batch of one, and handles sequences of different lengths. That is why Transformers use LayerNorm rather than BatchNorm (see <Term slug="layer-normalization" />).<Cite id="ba2016" /> Feeding the single example $[1, 2, 3, 6]$ (four features) to `nn.LayerNorm(4)` gives the same $[-1.069, -0.535, 0, 1.604]$ as above: the arithmetic is identical, but the averaging runs along the other axis.

<Callout type="tip">
A `Linear` layer followed directly by BatchNorm does not need its own bias, because BatchNorm subtracts the mean and adds $\beta$ anyway. Write `nn.Linear(784, 256, bias=False)`.
</Callout>

## Summary

- Weights must start random (to break symmetry) and scaled to the layer size (to keep the signal size constant).
- Use He initialization ($\text{Var} = 2/n_\text{in}$) for ReLU and Xavier ($2/(n_\text{in}+n_\text{out})$) for tanh or sigmoid; PyTorch's defaults are fine for small networks.
- BatchNorm normalizes each feature over the batch and then applies a learned scale and shift; in `eval()` mode it uses running statistics.
- LayerNorm normalizes each example over its features, so it needs no batch and is the standard choice in Transformers.
