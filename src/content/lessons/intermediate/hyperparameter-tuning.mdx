A **hyperparameter** is a setting that you choose rather than one the training algorithm learns: the learning rate, batch size, number of layers, dropout rate and weight decay are all examples.<Cite id="goodfellow2016-guidelines" /> The weights and biases, by contrast, are **parameters**, set by the optimizer. Good hyperparameters often decide whether a model trains at all, so tuning them systematically is one of the main skills of practical deep learning.<Cite id="tuning-playbook" />

## Parameters and hyperparameters

| | Parameters | Hyperparameters (see <Term slug="hyperparameter" />) |
|---|---|---|
| Examples | Weights, biases, BatchNorm's $\gamma$ and $\beta$ | Learning rate, batch size, epochs, width, depth, dropout, weight decay, schedule |
| Set by | `optimizer.step()`, from gradients | You, before or around training |
| Chosen using | The training set | The **validation** set |

Hyperparameters must be chosen on a validation set, never on the test set. Every decision made by looking at a dataset fits the model a little to that dataset, so a test set used for decisions no longer gives an honest score.<Cite id="goodfellow2016-guidelines" /><Cite id="cs231n-nn3" />

<Analogy breaks="An oven's dials have a known effect; a network's hyperparameters interact in ways you only discover by running experiments.">
Hyperparameters resemble an oven's temperature and timer dials, and parameters are the cake itself. You set the dials, the cake forms on its own, and you judge the dials by tasting a test slice (the validation set), not by eating the cake you will serve to guests (the test set).
</Analogy>

## What to tune first

The <Term slug="learning-rate" /> is usually the most important hyperparameter. Goodfellow and colleagues advise tuning it first if you can tune only one, because it controls the effective capacity of the model in a complicated way.<Cite id="goodfellow2016-guidelines" /> A practical order is:<Cite id="tuning-playbook" /><Cite id="cs231n-nn3" />

1. **Start from a known-good recipe**: an architecture and optimizer settings that worked for a similar problem, such as Adam at $10^{-3}$.
2. **Tune the learning rate** on a log scale (and the schedule, if any).
3. **Fix overfitting or underfitting** with regularization (weight decay, dropout, augmentation) or model size, as described in [Overfitting and regularization](/course/intermediate/overfitting-regularization/).
4. **Fine-tune the rest** (Adam's betas, warmup length) only if budget remains.

Google's *Deep Learning Tuning Playbook* frames this as an incremental strategy. Each round of experiments has one goal, and the hyperparameters are sorted into *scientific* ones (whose effect you want to measure), *nuisance* ones (which must be re-tuned for a fair comparison, such as the learning rate), and *fixed* ones.<Cite id="tuning-playbook" /> A change is adopted only when the evidence is clear.

### Batch size

The playbook recommends choosing the batch size for training *speed* and hardware fit, not as a knob for validation accuracy. With the other hyperparameters re-tuned, roughly the same final performance is reachable across a wide range of batch sizes.<Cite id="tuning-playbook" /> The catch is "re-tuned": changing the batch size changes the best learning rate, so search the learning rate again after changing it.

## The learning-rate range test

Leslie Smith proposed a cheap way to find a sensible range for the learning rate: train briefly while increasing the rate step by step, and watch where the loss starts to fall and where it becomes unstable.<Cite id="smith2015" /> A common variant raises the rate exponentially, by the same factor at every mini-batch, from a tiny value to a huge one.

The result is a starting point, not an answer: confirm it with a few short training runs.<Cite id="smith2015" />

## Random search

When several hyperparameters matter, try combinations. Two rules from the CS231n notes and the literature apply:<Cite id="cs231n-nn3" />

- **Sample on a log scale.** Learning rates and weight decay matter by factors of ten, so draw $u$ uniformly and use $10^u$.
- **Prefer random search to grid search.** Bergstra and Bengio showed that when only a few hyperparameters matter, random points test many more distinct values of each important one than a grid with the same number of trials.<Cite id="bergstra2012" /> The playbook prefers quasi-random sequences for the same reason.<Cite id="tuning-playbook" />

Search coarse to fine: a wide range with short runs first, then a narrower range around the best region with longer runs. If the best value sits at the edge of your range, extend the range.<Cite id="cs231n-nn3" />

### Budget and bookkeeping

Decide the budget before starting, for example "20 runs of 5 minutes", and keep every run comparable: same data split, same number of steps, fixed seeds.<Cite id="tuning-playbook" /> Record each run's hyperparameters, seed, code version and validation curve. A CSV file is enough; [TensorBoard](https://docs.pytorch.org/docs/stable/tensorboard.html), which PyTorch supports through `torch.utils.tensorboard`, adds plots.<Cite id="pt-tensorboard" /> Without records it is impossible to tell later which change actually helped.

<Callout type="pitfall">
Changing several hyperparameters at once "to save time" makes it impossible to know which change mattered. Change one thing per comparison, or use a proper random search.
</Callout>

## Summary

- Parameters are learned by the optimizer; hyperparameters are chosen by you, using the validation set only.
- Tune the learning rate first, on a log scale; then regularization and model size; then the rest.
- An LR range test finds a sensible starting rate in one short run; random search beats grid search when few settings matter.
- Fix a budget, keep runs comparable, record everything, and change one thing at a time.
