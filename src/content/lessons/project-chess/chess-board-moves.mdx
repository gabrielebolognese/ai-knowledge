Before a chess engine can think about a position, it needs a **board representation**: a data structure that records where every piece stands, whose turn it is, and the few extra facts the rules depend on, plus a function that lists every legal move.<Cite id="cpw-board" /> This lesson uses the python-chess library for both, writes positions as text in <Term slug="fen">FEN</Term>, and builds a small <Term slug="perft" /> function that counts how fast the tree of possible moves grows.<Cite id="python-chess-core" /> Every later lesson in this track, starting with [Material and piece-square tables](/course/project-chess/chess-evaluation/), builds on these few calls.

## Installing python-chess

The library is published on PyPI under the name `chess`, not `python-chess`, and it is imported as `import chess`.<Cite id="pypi-chess" /> It is released under the GPL-3 licence, and the current release needs Python 3.11 or newer.<Cite id="pypi-chess" />

```bash
pip install chess
python -c "import chess; print(chess.__version__)"
```

The companion code was tested with version 1.11.2. Writing a move generator yourself is a classic exercise, but it costs a lot of debugging time around castling, en passant, pins and promotions, so this project reuses a mature one and spends the effort on search and evaluation instead.

## Writing positions in FEN

**Forsyth-Edwards Notation** (FEN) describes a whole position in one line of text.<Cite id="cpw-fen" /> The start position is:

```text
rnbqkbnr/pppppppp/8/8/8/8/PPPPPPPP/RNBQKBNR w KQkq - 0 1
```

The line has six fields separated by spaces:<Cite id="cpw-fen" />

1. **Piece placement**, rank 8 first and rank 1 last, ranks separated by `/`. Upper-case letters are White pieces, lower-case are Black, and a digit counts empty squares.
2. **Side to move**: `w` or `b`.
3. **Castling rights**: any of `KQkq`, or `-` when nobody can castle.
4. **En passant target square**, the square a pawn skipped over on a double step, or `-`.
5. **Halfmove clock**: plies since the last capture or pawn move, used for the 50-move rule.
6. **Fullmove number**, which starts at 1 and grows after each Black move.

In python-chess, `chess.Board(fen)` reads a FEN and `board.fen()` writes one; `chess.Board()` with no argument gives the start position.<Cite id="python-chess-core" />

<Callout type="note">
After `1.e4`, python-chess writes `rnbqkbnr/pppppppp/8/8/4P3/8/PPPP1PPP/RNBQKBNR b KQkq - 0 1` with `-` in the en passant field. By default it lists the en passant square only when an en passant capture is actually legal, while the FEN standard writes `e3` after any double pawn step; `board.fen(en_passant="fen")` gives the strict form.<Cite id="python-chess-core" /><Cite id="cpw-fen" /> Both describe the same position.
</Callout>

## How programs store the board

The simplest representation is a **mailbox**: an array of 64 squares (or 120, with a border of sentinel squares that makes off-board moves easy to detect), each holding a piece or "empty".<Cite id="cpw-board" /> Strong engines use **bitboards** instead: one 64-bit integer per piece type and colour, with one bit per square, so a single machine word covers the whole board.<Cite id="cpw-bitboards" /> Questions such as "which squares do White's pawns attack?" then become a few shifts and bitwise operations instead of a loop over squares.<Cite id="cpw-bitboards" />

<Analogy breaks="Real overlays are only looked at, while bitboards are combined with arithmetic, and a position also needs facts no overlay shows: side to move, castling rights, en passant and the move counters.">
Bitboards are like twelve transparent sheets laid on the board, one per kind of piece, each with dots where those pieces stand. Asking where the white pawns attack means sliding one sheet up a row and diagonally.
</Analogy>

python-chess uses bitboards internally and exposes them as plain Python integers, for example `board.pieces_mask(chess.KNIGHT, chess.WHITE)`. Squares are numbered from `a1 = 0` to `h8 = 63`.<Cite id="python-chess-core" /> You rarely need the bitboards directly in this project, but the evaluation lesson uses them to count pieces quickly.

## Legal moves, push and pop

`board.legal_moves` lists every **legal** move: moves that would leave your own king in check are already removed.<Cite id="python-chess-core" /> `board.push(move)` plays a move and `board.pop()` takes the last one back, so the same board object can walk down a line and back up again.<Cite id="python-chess-core" />

```python
import chess

board = chess.Board()                     # start position
print(board.legal_moves.count())          # 20
board.push_san("e4")                      # standard algebraic notation
board.push(chess.Move.from_uci("e7e5"))   # or UCI text: from-square, to-square
print(board.fen())   # rnbqkbnr/pppp1ppp/8/4p3/4P3/8/PPPP1PPP/RNBQKBNR w KQkq - 0 2
board.pop()                               # back to the position after 1.e4
```

This make/unmake pattern is the heartbeat of every search in the track. A search plays a move, looks at the resulting position, and undoes the move, millions of times per game, so it reuses one board rather than copying it at every step. The board also remembers the moves played (`board.move_stack`), which the search later needs to detect repeated positions.<Cite id="python-chess-core" />

## The exponential tree

Each legal move leads to a new position with its own legal moves, so the possible futures form a tree that branches at every **ply** (one move by one side). The number of positions at each depth grows roughly by a constant factor per ply, called the **branching factor** $b$.<Cite id="cpw-perft-results" /><Cite id="cpw-minimax" />

The published start-position counts continue with 4,865,609 at depth 5 and 119,060,324 at depth 6.<Cite id="cpw-perft-results" /> This explosion is why an engine cannot simply look at every line: plain <Term slug="minimax" /> search visits every leaf of this tree, and the [alpha-beta lesson](/course/project-chess/chess-alpha-beta/) shows how to skip most of them without changing the answer.<Cite id="cpw-minimax" />

## Perft: counting the tree

**Perft** (short for "performance test") walks the legal-move tree to a fixed depth and counts the leaves.<Cite id="cpw-perft" /> Its main use is debugging move generators: the correct counts for many test positions are published, so any mismatch proves a bug, and the count also serves as a simple speed benchmark.<Cite id="cpw-perft" /><Cite id="cpw-perft-results" />

| Position | Depth 1 | Depth 2 | Depth 3 | Depth 4 |
|---|---|---|---|---|
| Start position | 20 | 400 | 8,902 | 197,281 |
| "Kiwipete" (busy middlegame) | 48 | 2,039 | 97,862 | 4,085,603 |

The second row comes from a position nicknamed Kiwipete, `r3k2r/p1ppqpb1/bn2pnp1/3PN3/1p2P3/2N2Q1p/PPPBBPPP/R3K2R w KQkq -`, built so that castling, en passant, promotions and pins all appear within a few plies.<Cite id="cpw-perft-results" /> Its tree is much bushier: 48 moves at the root instead of 20.

Two tricks make perft practical. **Bulk counting** stops one ply early and adds up the number of legal moves at the last level instead of playing each one.<Cite id="cpw-perft" /> **Divide** prints a separate count under each root move, so a wrong total can be traced to one branch, then one position, then one move.<Cite id="cpw-perft" />

<Callout type="tip">
python-chess is already well tested, so your perft will match the table. The point here is to see the exponential tree with your own eyes and to have a reference: if you ever write your own move generator, perft against python-chess is how you test it.
</Callout>

## Summary

- Install the library with `pip install chess` and import it as `chess`.
- FEN stores a position in six fields: pieces, side to move, castling, en passant, halfmove clock and move number.
- Engines store the board as a mailbox array or as bitboards; python-chess uses bitboards internally.
- `legal_moves`, `push` and `pop` let one board walk down a line and back, which is how every search works.
- The move tree grows by roughly $b^d$, and perft counts it exactly: 20, 400, 8,902, 197,281 from the start position.
