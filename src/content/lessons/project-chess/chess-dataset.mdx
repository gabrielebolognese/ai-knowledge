A neural evaluator needs examples: positions paired with a good score. The **Lichess evaluation database** supplies hundreds of millions of positions that Stockfish has already analysed, and it is free to use under CC0, a public-domain dedication.<Cite id="lichess-db" /> This lesson turns the first few hundred thousand of them into a training set: streamed instead of downloaded, filtered to quiet positions, and encoded as the 768 features the network in the [next lesson](/course/project-chess/chess-train-evaluator/) will read.

Lichess publishes its game, puzzle and evaluation exports at database.lichess.org, all under CC0, so the data may be used and shared without conditions.<Cite id="lichess-db" /> The code that produces the exports is open source.<Cite id="lichess-github" /> The evaluation file listed 417,862,375 positions evaluated with Stockfish when its page was last updated on 2026-11-11, and its HTTP `Content-Length` on 2026-11-24 was about 22.5 GB.<Cite id="lichess-db" />

### One line of the file

Each line is a JSON object with two fields. `fen` is the position in <Term slug="fen">FEN</Term>, but only the first four parts (pieces, side to move, castling, en passant), without the move counters. `evals` is a list of analyses, each with `knodes` (thousands of nodes searched), `depth` and `pvs`. Every principal variation (PV) has either `cp`, a score in <Term slug="centipawn">centipawns</Term>, or `mate`, when a forced mate was found, plus `line`, the moves in UCI_Chess960 notation.<Cite id="lichess-db" />

A position can have several analyses. Lichess recommends taking the evaluation with the **highest depth** and using its **first PV** if you only want one score, which is what `best_eval` does.<Cite id="lichess-db" /> The first move of that PV is the best move, which the filters below need.

## Streaming instead of downloading

Nobody needs all 22.5 GB for a first network. The companion code opens the file over HTTPS and passes the response to a Zstandard decompressor from the `zstandard` package, which can read a compressed stream piece by piece.<Cite id="python-zstandard" /> Lines are decoded one at a time, and the loop simply stops after the requested number of records, so only the beginning of the file is ever transferred. Interrupting it with Ctrl+C is safe.

An alternative is the Parquet copy of the same data on Hugging Face, split into many files, so you can download one slice and read it with any Parquet reader.<Cite id="lichess-evals-hf" /> The streaming route needs no extra tooling beyond `zstandard` and reads the official file directly.

## Choosing the score and its sign

Lichess reports `cp` from **White's** point of view: +50 means White is half a pawn better, whoever is to move.<Cite id="lichess-db" /> The search, however, uses negamax, which needs every score from the point of view of the **side to move** (the [evaluation lesson](/course/project-chess/chess-evaluation/) made the same conversion for the hand-written tables). `to_example` keeps the score when White is to move and negates it when Black is to move, then clips it to ±2000 cp, because beyond that every position is simply winning.

<Callout type="pitfall">
A sign bug here is silent: the network still trains and the loss still falls, but it learns that being a queen up is bad whenever Black is to move. `data.py` runs `self_check` before every build. It asserts that a White-relative +40 after 1.e4 becomes −40 for Black to move, and that a position and its colour-mirrored copy produce the same features.
</Callout>

## Filtering: keep quiet, legal positions

Not every record makes a useful example. `to_example` returns nothing for:

- **Mate scores.** A mate has no centipawn value, and finding mates is the search's job, not the evaluator's.
- **Invalid FENs and illegal positions.** Some analysed positions were set up by users and are impossible in a game; python-chess's `Board.is_valid()` catches them.<Cite id="python-chess-core" />
- **Positions where the side to move is in check.** The engine never evaluates these statically: it searches the evasions instead.
- **Positions whose best move is a capture or a promotion.** Their score depends on a tactic that has not happened yet, so the board and the score disagree.

The engine's quiescence search resolves captures before it calls the evaluator, so the network will mostly be asked about quiet positions; training on quiet positions matches that. The official Stockfish trainer applies a similar skip of capture and in-check positions while loading its data.<Cite id="nnue-pytorch" /> Castling in UCI_Chess960 notation is written as the king moving onto its own rook's square, and python-chess's `is_capture` correctly does not count it as a capture.<Cite id="python-chess-core" />

On the companion run, these filters kept 300,000 of the first 512,708 records, about 59%. The bundled offline sample of 4,000 records keeps 2,255 (56%).

<Callout type="warning">
These are positions that Lichess users chose to analyse, mostly from human games, at varying depths and with different Stockfish versions. That is fine for learning, but it is not a curated training set like the one Stockfish itself is trained on, and the network will inherit whatever biases the selection has.
</Callout>

## Encoding: 768 piece-square features

The network's input has one slot for each combination of 2 colours × 6 piece types × 64 squares: 768 inputs, each 1 if that piece stands on that square and 0 otherwise. This is the simple "A" feature set from the official NNUE documentation.<Cite id="nnue-doc" /><Cite id="cpw-nnue" /> At most 32 inputs are on, so the code stores only the list of active indices.

The features are seen from the side to move's chair. Slots 0-383 hold the mover's own pieces and 384-767 the opponent's, and when Black is to move the board is flipped vertically, so "my pawn about to promote" is the same input for both colours.<Cite id="nnue-doc" /> python-chess numbers the squares a1 = 0, b1 = 1, …, h8 = 63, and `chess.square_mirror` does the flip.<Cite id="python-chess-core" />

### Storage

`encode` writes each position as a fixed row of 32 `int16` indices, padding unused slots with 768 ("no feature"), and the score is one more `int16`. That is 66 bytes per position, so one million positions take about 66 MB in memory. The arrays are saved as a compressed NumPy `.npz`; the 300,000-position run produced a 5.0 MB file, with about 23.8 active features per position on average.

## Summary

- The Lichess evaluation export holds 417,862,375 Stockfish-scored positions under CC0; stream the start of it with `zstandard`, or download Parquet slices from Hugging Face.
- Take the deepest evaluation and its first PV, then convert the White-relative score to the side to move; `self_check` guards against the sign bug.
- Keep only quiet, legal positions: no mates, no check, no capture or promotion as best move (59% of records survived).
- Each position becomes up to 32 of 768 feature indices, $(0 \text{ or } 384) + (t-1) \cdot 64 + s$, about 66 bytes per position before compression.
