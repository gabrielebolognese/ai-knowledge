**Negamax with alpha-beta pruning** is the search at the heart of classic chess engines: it looks several moves ahead, assumes both sides always pick their best reply, and returns the move with the best guaranteed outcome.<Cite id="cpw-negamax" /> Alpha-beta pruning gives exactly the same answer as a full <Term slug="minimax" /> search while skipping branches that cannot change it, often most of the tree.<Cite id="cpw-alphabeta" /> This lesson traces the algorithm by hand, then reads the companion `Searcher.negamax`, which also handles checkmate, stalemate and draws.

## Minimax written once: negamax

Minimax alternates two rules: on my turn take the move with the **highest** score, on the opponent's turn assume the **lowest**.<Cite id="cpw-minimax" /> Negamax writes both as one rule, using the identity $\max(a, b) = -\min(-a, -b)$. If $V(p)$ is the value of position $p$ for the player to move, then $V(p) = \max_m \big(-V(p \text{ after } m)\big)$: a position worth +3 to my opponent, who moves next, is worth −3 to me.<Cite id="cpw-negamax" />

At the leaves the search calls the evaluation, which must also score from the side to move's point of view; that is why the [evaluation lesson](/course/project-chess/chess-evaluation/) negates its score when Black is to move.<Cite id="cpw-negamax" /> The cost is the problem: with about 35 moves per position, a full 6-ply tree has about 1.8 billion leaves.

## The alpha-beta window

<Term slug="alpha-beta-pruning">Alpha-beta</Term> carries two bounds down the tree.<Cite id="cpw-alphabeta" />

- $\alpha$ (alpha) is the score the side to move is **already guaranteed** by a move it has searched.
- $\beta$ (beta) is the most the **opponent will allow**: they already have a better option elsewhere, so a line scoring $\beta$ or more will never be reached.

When a move scores at least $\beta$, the rest of the moves at that node do not matter: the opponent will avoid this position anyway. Stopping there is a **beta cutoff**. In negamax the window is handed to the child with signs flipped and swapped, $(-\beta, -\alpha)$, because one player's floor is the other's ceiling.<Cite id="cpw-alphabeta" /> The Chessprogramming Wiki stresses that this saving comes "without any potential of overlooking a better move".<Cite id="cpw-alphabeta" />

<Analogy breaks="A fare can only go up as you read on, but in a game tree the opponent's later replies can be anything; the cutoff is safe only because the opponent will pick the worst one for you.">
You are shopping for a flight and already hold a €100 ticket. The next airline's cheapest fare starts at €140, so you close that site without reading the rest of its offers.
</Analogy>

Order matters. If B is searched first, it returns its worst reply, 1, so $\alpha = 1$; then every reply of A (5, 3, 6) is above 1, nothing is cut off, and all six leaves are evaluated. Alpha-beta always returns the minimax value, but how much it saves depends on searching good moves first.<Cite id="cpw-alphabeta" />

## How much can it save?

Donald Knuth and Ronald Moore analysed the algorithm in 1975.<Cite id="knuth1975" /> In the worst move order alpha-beta evaluates as many leaves as minimax; with the best move always searched first it needs far fewer.<Cite id="cpw-alphabeta" /><Cite id="knuth1975" />

Real engines land between the two cases, which is why the [move ordering lesson](/course/project-chess/chess-ordering-quiescence/) is worth so much.<Cite id="cpw-alphabeta" />

## Mate, stalemate and draws

When the side to move has **no legal moves**, the game is over and the evaluation is not called. In check, that is checkmate; otherwise it is stalemate, a draw, scored 0.<Cite id="python-chess-core" /> The companion code sets $\text{MATE} = 100{,}000$ and scores "checkmated at ply $p$" as $-\text{MATE} + p$, so a mate the engine delivers in $n$ plies is worth $\text{MATE} - n$. The engine therefore prefers the fastest mate and, when losing, the slowest one. Mate scores are converted to the UCI form `mate 1`, `mate 2` (moves, not plies) when printed.

Draws by rule are scored 0 as well. The 50-move rule is a halfmove clock of 100 or more.<Cite id="python-chess-core" /> For repetitions, the search keeps a set of position fingerprints, the Zobrist keys from `chess.polyglot.zobrist_hash`, for every position of the game so far and of the current search path, and returns 0 when a position comes back.<Cite id="python-chess-polyglot" /> The official rule needs a threefold repetition before a draw can be claimed; treating the first repeat inside the search as a draw is a common simplification in engines.<Cite id="python-chess-core" />

<Callout type="pitfall">
Repetition checks must include the positions already played in the game, not only those on the search path. Otherwise the engine cannot see that a move repeats an earlier position, and it may walk into a draw while winning, or miss a saving draw while losing. `search()` fills the set from `board.move_stack` before the first iteration.
</Callout>

Two smaller refinements live in the same function. A **check extension** searches one ply deeper when the side to move is in check, so a line never ends in the middle of a check sequence. **Mate-distance pruning** narrows the window to the best and worst mate scores still possible at this ply, and stops when no line could improve on a mate already found.

## Counting nodes: the yardstick

Every later improvement in this track is judged by one test: the **same best move with fewer nodes**. The file keeps a plain negamax without pruning, `minimax`, as the reference:

<CodeFile path="code/projects/project-chess/search.py" lines="381-395" highlight="393" title="search.py: the no-pruning reference" />

To compare, search the start position 3 plies deep with both, turning off ordering, quiescence and the transposition table in the `Searcher` so that only pruning differs:

```python
import chess
from search import minimax, Searcher
from eval_material import evaluate, MaterialEvaluator

board, counter, scores = chess.Board(), [0], {}
for move in board.legal_moves:
    board.push(move)
    scores[move] = -minimax(board, 2, evaluate, counter)
    board.pop()
best = max(scores, key=scores.get)
print("minimax   ", board.san(best), scores[best], counter[0], "nodes")

r = Searcher(MaterialEvaluator(), use_ordering=False, use_qsearch=False, use_tt=False).search(board, max_depth=3)
print("alpha-beta", board.san(r.move), r.score, r.nodes, "nodes")
```

On the test machine both chose `Nf3` with a score of +50; minimax visited 9,322 nodes (20 + 400 + 8,902, every position of the tree), and alpha-beta 883, even counting its depth-1 and depth-2 iterations. When several moves share the best score the two may pick different moves of equal value, so compare the **scores** first.

- Mate in 2, `k7/8/2K5/8/8/8/8/7R w - - 0 1`: `Kc7` (`Kb6` also mates in two), `mate 2` at depth 3 in about 400 nodes. A mate in 2 is three plies deep, and the search stops as soon as the mate is proven, so it never needs the fourth ply.
- A free queen, `rnb1kbnr/ppp1pppp/8/3q4/4P3/8/PPPP1PPP/RNBQKBNR w KQkq - 0 1`: `exd5`, about +975 cp.

For a larger test set, the Lichess puzzle database is free under CC0: about 6.2 million rated puzzles in a CSV file with columns such as `FEN`, `Moves`, `Rating` and `Themes`.<Cite id="lichess-db" /> The first move in `Moves` is the opponent's move that sets up the puzzle, so play it before searching.<Cite id="lichess-db" /> A useful milestone measure is the share of puzzles in a rating band that the engine solves at a fixed depth or time per move.

## Summary

- Negamax is minimax written once: $V(p) = \max_m (-V(p \text{ after } m))$, with a side-to-move evaluation at the leaves.
- Alpha-beta keeps a window $[\alpha, \beta]$ and stops searching a node once a move scores at least $\beta$; the result equals minimax.
- Savings depend on move order: from $b^d$ leaves down to $b^{\lceil d/2 \rceil} + b^{\lfloor d/2 \rfloor} - 1$, for $b = 40, d = 6$ from 4,096,000,000 to 127,999.
- Checkmate scores $-\text{MATE} + \text{ply}$, stalemate and rule draws score 0, and repetitions must include the game history.
- Count nodes: every later improvement must find the same move with fewer of them.
