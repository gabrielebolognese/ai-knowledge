**Iterative deepening** searches a position to depth 1, then 2, then 3 and so on until the time is up, and plays the best move of the last completed search.<Cite id="cpw-id" /> It is paired with a **transposition table**, a memory of positions already searched, keyed by a **Zobrist hash** of each position.<Cite id="cpw-tt" /> Together they let the engine respect a clock and reuse work that plain alpha-beta throws away.

## Iterative deepening

A depth-first search has no useful answer until it finishes, and nobody knows in advance how long depth 6 will take. Iterative deepening sidesteps the problem: each finished depth leaves a complete answer behind, and the Chessprogramming Wiki calls it the basic time-management strategy of depth-first search.<Cite id="cpw-id" /> The earlier iterations also feed the next one: their best moves go into the transposition table and come back as the first move to try.<Cite id="cpw-id" />

<Analogy breaks="An exam answer is refined in place; each new iteration starts the search again from the root and only reuses the earlier work through the table and the move ordering.">
It works like a student who first answers every exam question roughly, then goes back to improve the answers. When the bell rings, there is always a full answer sheet to hand in.
</Analogy>

### Why it costs so little

Re-searching the shallow depths sounds wasteful, but each extra ply multiplies the work by the *effective branching factor* $b$, the growth of the node count per ply after pruning. With good ordering alpha-beta visits roughly the square root of the number of leaves that minimax would, so this factor is much smaller than the 30-40 legal moves of a middlegame.<Cite id="cpw-alphabeta" /> Even so, the last iteration dominates the total.

  <Step tex="b = 6:\ \frac{6}{5} = \hl{1.2}" words="All the shallow iterations together add about 20% to the cost of the last one." example="depth 4: 6 + 36 + 216 + 1296 = 1554, and 1554 / 1296 ≈ 1.20" />

The companion code behaves close to this. In one measured run on the start position to depth 5, the whole search took 20,367 nodes and the last iteration alone 17,150, so the four shallower iterations added about 19%. The better move ordering they provide usually repays that.<Cite id="cpw-id" />

### Time limits and the stop flag

`Searcher.search` uses three limits. A **hard deadline** at the full time budget, a node limit, and a **stop flag** (a `threading.Event` that the UCI `stop` command sets) are checked every 1,024 nodes; when one trips, the search raises `SearchStopped` and unwinds at once. A partly finished iteration is mostly discarded: its root move is kept only if it beat the previous best after a full search of that move.

The **soft limit** decides whether to start another depth at all. The next iteration costs several times the one just finished, so the code does not begin a new one after 45% of the budget has gone; starting it would usually mean throwing it away. The search also stops early once a forced mate is fully proved. How the budget is set from the game clock is part of the [UCI capstone](/course/project-chess/chess-uci-elo/).

## Zobrist hashing

Different move orders often reach the same position: 1.Nf3 Nf6 2.Nc3 and 1.Nc3 Nf6 2.Nf3 are one position. These repeats are called *transpositions*. To recognise them quickly, the engine needs a short fingerprint of a position, and the standard one is the **Zobrist hash**, invented by Albert Zobrist in 1970.<Cite id="cpw-zobrist" />

<Term slug="zobrist-hashing" /> gives every (piece, square) pair a fixed random 64-bit number, plus numbers for the side to move, the castling rights and the en-passant file. A position's key is the exclusive or (XOR) of the numbers of everything present.<Cite id="cpw-zobrist" /> XOR undoes itself ($x \oplus x = 0$), so a quiet move updates the key with just two XORs: one to take the piece off its old square and one to put it on the new one, plus one for the change of side to move.<Cite id="cpw-zobrist" />

>

  <Step tex="h = R \oplus N_{g1} = \hl{1110}" words="The key of the position with the knight on g1." />
  <Step tex="h \oplus \hl{N_{g1}} = 1110 \oplus 1011 = 0101" words="XOR the g1 number again: the knight is lifted off and only R is left." />
  <Step tex="0101 \oplus \hl{N_{f3}} = 0101 \oplus 0110 = 0011" words="XOR in the f3 number: the knight lands on f3." />

</MathSteps>

<Analogy breaks="A fingerprint is unique to a person; two different positions can share a Zobrist key, though with 64 bits that is rare.">
A Zobrist key is a fingerprint that can be updated by dabbing two fingers instead of rescanning the whole hand.
</Analogy>

With 64-bit keys collisions are rare in practice; with 32-bit keys the birthday bound makes them likely after only about $2^{16}$ positions.<Cite id="cpw-zobrist" /> The companion code does not build its own keys: it calls `chess.polyglot.zobrist_hash(board)`, which computes the key used by the Polyglot opening-book format.<Cite id="python-chess-polyglot" /> That function rebuilds the key from the whole board on each call rather than with two XORs, which is simple but not the fastest choice in Python. If hashing shows up when you profile the engine, an incremental key of your own is worth measuring. The same keys also detect repetitions: the search keeps a set of the keys of positions from the game (replayed from python-chess's `board.move_stack`) and from the current path, and scores a repeat as a draw.<Cite id="python-chess-core" />

## The transposition table

The <Term slug="transposition-table" /> is a Python dictionary from Zobrist key to a tuple `(depth, flag, score, move)`. It holds up to 1,000,000 entries and, as the simplest possible replacement scheme, is cleared when it fills. The idea is old: the first transposition table appeared in Richard Greenblatt's Mac Hack VI.<Cite id="cpw-tt" />

### Exact, lower and upper bounds

Because alpha-beta searches with a window, the score it returns is not always exact. The table records which kind it got:<Cite id="cpw-tt" />

| Flag | When it is stored | What the score means |
|---|---|---|
| EXACT | The best score landed inside the window | The true value |
| LOWER | A move reached beta (a cutoff) | The true value is at least this |
| UPPER | Every move failed to beat alpha | The true value is at most this |

When the same position comes up again, an entry may end the search only if it came from a search **at least as deep** as the one needed now. Then an EXACT score is returned directly, a LOWER score if it is at least beta, and an UPPER score if it is at most alpha.<Cite id="cpw-tt" /> Otherwise the stored move is still used as the hash move for ordering. In a measured run to depth 5, turning the table off left the move and score unchanged but raised the node count from 20,367 to 30,372 on the start position, and from 111,999 to 225,866 in the Italian Game position of the benchmark; that saving includes the lost hash move as well as the reused scores.

<Exercise id="chess-iterative-deepening-tt-bound" />

### Mate scores and the ply

The engine scores "checkmated right now" as $-\text{MATE}$ with $\text{MATE} = 100{,}000$, and a mate found $n$ plies from the root as $\text{MATE} - n$, so it prefers the fastest win and the slowest loss. That number counts from the root, but a table entry may be reused at a different ply. The code therefore converts mate scores to "plies from this node" when storing (add the ply) and back to "plies from the root" when probing (subtract the current ply).<Cite id="cpw-tt" />

<Callout type="pitfall">
Storing mate scores in the table without the ply adjustment is a classic bug. The engine then reports wrong mate distances, can prefer a slower mate to a faster one, and can blunder into a mate it believed was further away.<Cite id="cpw-tt" />
</Callout>

## Summary

- Iterative deepening searches depth 1, 2, 3 … and always has the last completed answer ready; the shallow iterations cost about $b/(b-1)$ of the last, roughly 20% for $b = 6$.
- The search stops on a hard deadline, a node limit or a stop flag, and does not start a new depth after 45% of its time.
- Zobrist keys are XORs of random numbers, so a move updates them with a few XORs; python-chess provides them through `chess.polyglot.zobrist_hash`.
- A transposition table stores depth, an EXACT, LOWER or UPPER flag, the score and the best move; stored scores may only cut the search when their depth is enough.
- Mate scores must be converted between "from the root" and "from this node" when they enter and leave the table.
