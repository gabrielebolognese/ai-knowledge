A **<Term slug="virtual-environment" />** is a folder, by convention called `.venv`, that holds a private Python and the packages installed for one project. Each project gets its own, so installing or upgrading a package for one project can never break another.<Cite id="py-venv" /> The Python Packaging guide recommends installing packages inside one rather than into the system Python.<Cite id="pypa-venv-guide" />

<Analogy breaks="Lab benches cost money and space; a virtual environment is just a folder, so you can make, delete and rebuild them freely.">
A virtual environment is a clean lab bench for one experiment. Chemicals from one bench never contaminate another, and if a bench gets messy you clear it and set it up again from the list of what belongs there.
</Analogy>

## Step 1. Make the course folder

Use a short path **outside OneDrive, Dropbox or iCloud**. A virtual environment holds thousands of small files; sync services slow it down and can corrupt it.

| Windows (PowerShell) | macOS / Linux |
|---|---|
| `mkdir C:\dev\ai-knowledge` | `mkdir -p ~/dev/ai-knowledge` |
| `cd C:\dev\ai-knowledge` | `cd ~/dev/ai-knowledge` |
| `code .` | `code .` |

`code .` opens the folder in VS Code. Short paths also avoid Windows' old 260-character path limit, which can break package installs.<Cite id="py-using-windows" />

## Step 2. Create the environment

In the terminal, inside the course folder (VS Code's own terminal works too: **Terminal → New Terminal**):

| Windows | macOS / Linux |
|---|---|
| `python -m venv .venv` | `python3 -m venv .venv` |

With the Windows install manager you can pin the version: `py -V:3.14 -m venv .venv`. The command takes a few seconds and prints nothing.<Cite id="py-venv" />

**Verify it worked:** a folder named `.venv` appears (`dir` or `ls -a`; in VS Code's Explorer on the left).

## Step 3. Activate it

Activation makes `python` and `pip` in this terminal point at the environment. The command depends on your shell:<Cite id="py-venv" />

| Shell | Command |
|---|---|
| **PowerShell** (Windows default) | `.venv\Scripts\Activate.ps1` |
| Command Prompt (cmd.exe) | `.venv\Scripts\activate.bat` |
| macOS / Linux (zsh, bash) | `source .venv/bin/activate` |
| fish | `source .venv/bin/activate.fish` |

**Verify it worked:** the prompt now starts with `(.venv)`, for example `(.venv) PS C:\dev\ai-knowledge>`. Run `python --version`: it shows the Python the environment was made with. To leave, type `deactivate`.

Activation lasts only for that terminal window. **Every new terminal needs it again**; VS Code does it for you once Step 5 is done.<Cite id="vscode-python-envs" />

### Windows: "running scripts is disabled on this system"

On a fresh Windows PC, `Activate.ps1` usually fails with a red message ending in *"cannot be loaded because running scripts is disabled on this system"*. Windows client editions block PowerShell scripts by default.<Cite id="ps-execution-policy" /> Allow local scripts for **your user only** (no administrator needed):

```powershell
Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser
```

Answer **Y** if asked, then run `.venv\Scripts\Activate.ps1` again. *RemoteSigned* runs scripts made on your PC and still demands a signature for scripts downloaded from the internet.<Cite id="ps-execution-policy" />

Two alternatives that need no policy change: use **Command Prompt** with `activate.bat`, or skip activation and call the environment's Python by its path, `.venv\Scripts\python.exe`; the venv docs note activation is optional.<Cite id="py-venv" />

## Step 4. Upgrade pip

<Term slug="pip" /> installs packages. Upgrade it first, always calling it **through Python**:

```text
python -m pip install --upgrade pip
```

`python -m pip` guarantees the packages go into the Python you are running, which is the active `.venv`.<Cite id="pip-user-guide" />

**Verify it worked:** `python -m pip --version` prints `pip 26.x from …\.venv\…`. The path must contain `.venv`; if it does not, the environment is not active.

<Callout type="pitfall">
On recent Ubuntu, Debian and Fedora, installing with pip **outside** a virtual environment fails with *"externally-managed-environment"*. This is deliberate, defined in PEP 668, to protect the system's own Python.<Cite id="pep-668" /> Activate `.venv` and the error disappears.
</Callout>

## Step 5. Tell VS Code to use it

1. In VS Code press **Ctrl+Shift+P** (**⌘⇧P** on macOS).
2. Type **Python: Select Interpreter** and press Enter.
3. Choose the entry with **`.venv`**, marked **Recommended**.<Cite id="vscode-python-envs" />

<Figure src="/screenshots/setup/ill-vscode-select-interpreter.svg" alt="Illustration of the VS Code Select Interpreter list with Python 3.14.10 ('.venv': venv), marked Recommended, outlined" caption="Illustration: (1) choose the .venv interpreter. **Verify it worked:** the status bar at the bottom right shows `3.14.10 ('.venv': venv)` or similar, and a **new** VS Code terminal opens with `(.venv)` already in the prompt.<Cite id="vscode-python-envs" />

## Summary

- One project, one `.venv`, in a short folder outside cloud sync.
- Create: `python -m venv .venv` (macOS/Linux: `python3`). Activate: `.venv\Scripts\Activate.ps1` or `source .venv/bin/activate`.
- PowerShell blocked? `Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser`.
- Always `python -m pip …`; check that `(.venv)` is in the prompt.
- In VS Code: **Python: Select Interpreter → `.venv`**.
