**Efficient inference** is the work of making a trained model cheaper to run: smaller files, less memory and lower latency, ideally without losing accuracy.<Cite id="pt-quantization" /> The main tools are **quantization** (fewer bits per number), **pruning** (fewer weights), **distillation** (a smaller model that imitates a larger one) and **export** to a fast runtime.<Cite id="han2015" /> The chess engine's NNUE-style evaluator adds a fifth: never recompute what has not changed.

## Where the cost goes

Size and speed are different budgets. Size is the number of parameters times the bytes per parameter; speed depends mostly on the number of multiply-adds. In the [digits CNN](/course/advanced/convolutional-networks/), 95% of the 421,642 parameters sit in the first fully connected layer, but the two convolutions, which reuse their small kernels at every pixel, perform about 3.8 million of the roughly 4.2 million multiply-adds per image. Shrinking fc1 therefore shrinks the file but barely changes the running time, as the measurement below confirms.

## Quantization: 32 bits down to 8

A float32 number takes 4 bytes; an 8-bit integer takes 1. <Term slug="quantization" /> maps each real value onto one of 256 evenly spaced levels. Jacob and colleagues at Google described the affine scheme used by most frameworks: a real value $r$ is stored as an integer $q$ with $r = S(q - Z)$, where the **scale** $S$ is the step between levels and the **zero-point** $Z$ is the integer that represents exactly 0.<Cite id="jacob2017" /> Representing zero exactly matters, because zero-padding and ReLU outputs produce many exact zeros.<Cite id="jacob2017" />

<Analogy breaks="A ruler's marks are fixed, while quantization picks its range and spacing separately for every tensor (or even every channel).">
Quantization is like measuring with a ruler that has only 256 marks: each length is rounded to the nearest mark, so the result is never off by more than half a mark.
</Analogy>

Quantization can also happen during training. Jacob and colleagues simulated the rounding in the forward pass while training, so the network learns weights that survive it; this is *quantization-aware training*.<Cite id="jacob2017" /> PyTorch's documentation distinguishes **dynamic** quantization (weights converted ahead of time, activations quantized on the fly, mainly for `Linear` and recurrent layers), **static** quantization (activations calibrated on sample data, needed for convolutions) and quantization-aware training.<Cite id="pt-quantization" />

## Pruning

<Term slug="network-pruning" /> removes weights that contribute little, usually those with the smallest magnitude, and then retrains the rest. In *Deep Compression*, Han, Mao and Dally combined pruning, which cut AlexNet's connections about 9 times, with quantization to a few shared values and Huffman coding. Together these shrank AlexNet 35 times, from 240 MB to 6.9 MB, and VGG-16 49 times, without loss of accuracy.<Cite id="han2015" />

The trade-off is that scattered zeros only save time when the software or hardware can skip them; ordinary dense matrix code multiplies the zeros anyway. PyTorch's `torch.nn.utils.prune` supports both this *unstructured* pruning and *structured* pruning, which removes whole channels and leaves a smaller dense layer that is faster with any software.<Cite id="pt-pruning" />

## Distillation

<Term slug="knowledge-distillation" /> trains a small *student* model to reproduce the outputs of a large *teacher*. Hinton, Vinyals and Dean softened the teacher's probabilities with a temperature $T$ in the softmax, $p_i = e^{z_i/T} / \sum_j e^{z_j/T}$.<Cite id="hinton2015" /> For logits $(5, 2, 1)$, $T = 1$ gives probabilities $(0.936, 0.047, 0.017)$, while $T = 4$ gives $(0.543, 0.257, 0.200)$, which reveals how the teacher ranks the wrong classes. Those relative probabilities carry information a one-hot label lacks, and the authors showed a small network trained on them comes much closer to the large one.<Cite id="hinton2015" />

The chess project uses the same principle. Its [768→256→32→1 evaluator](/course/project-chess/chess-train-evaluator/) is not trained on game results but on Stockfish's evaluations, so a 205,121-parameter network learns to imitate a far stronger teacher.

## Export to a runtime

Python and PyTorch are convenient for training but heavy to ship. <Term slug="onnx" /> ([onnx.ai](https://onnx.ai/)) is an open file format for neural networks, and `torch.onnx.export` writes a PyTorch model into it.<Cite id="pt-onnx" /> The file can then run in ONNX Runtime, which offers APIs for C++, C#, Java, JavaScript and other languages, and applies graph optimisations and hardware-specific acceleration.<Cite id="onnxruntime" /> The drawing apps in the vision projects could be served this way without installing PyTorch.

## Incremental updates: the NNUE idea

The most effective speed-up is to avoid work altogether. A chess engine evaluates millions of positions that differ by a single move. In Stockfish's <Term slug="nnue" />, the first layer's output, the *accumulator*, is the sum of the weight columns of the active piece-square features, so a quiet move needs only one column subtracted and one added instead of a full recomputation.<Cite id="nnue-doc" /> The project's model computes exactly that sum:

## Summary

- Size depends on parameters × bytes; speed depends on multiply-adds. Check which one you need to cut.
- Affine quantization stores $r = S(q - Z)$; 8 bits make weights 4 times smaller with an error of at most $S/2$.
- Dynamic quantization shrank the digits CNN 3.5 times at the same 98.91% accuracy, but not its running time.
- Pruning, distillation, ONNX export and incremental updates (NNUE) each trade effort, accuracy and portability differently.
