**Tokenization** is the step that turns text into a sequence of integers, called token ids, drawn from a fixed list called the vocabulary.<Cite id="hf-tokenizers-summary" /> A <Term slug="language-model" /> never sees letters: it sees these ids, looks each one up in an <Term slug="embedding" /> table and predicts the next id. How the text is cut decides how long the sequences are, how big the vocabulary is, and whether unfamiliar words can be represented at all.

## Characters, words or something in between

There are three common ways to cut text into tokens, and each makes a different trade.<Cite id="hf-tokenizers-summary" />

| Unit | Vocabulary | Sequence length | Unseen words |
|---|---|---|---|
| Character | tiny (65 for the Shakespeare file) | long | never a problem |
| Word | huge (hundreds of thousands) | short | become a single "unknown" token |
| Subword | chosen size (hundreds to ~100,000) | medium | split into known pieces |

Character models are the simplest to build, which is why the small-text project starts there. The cost is length: the model must spend capacity learning to spell, and a fixed context window covers fewer words. Word models fail on rare words and on code, where names such as `get_user_by_id` are invented all the time.<Cite id="sennrich2016" /> **Subword** tokenization keeps frequent words whole and splits rare ones into pieces, so every string can be encoded while common text stays short.<Cite id="sennrich2016" />

## Byte-pair encoding, merge by merge

Byte-pair encoding began in 1994 as a data-compression trick by Philip Gage: replace the most common pair of adjacent bytes with a new, unused byte, and repeat.<Cite id="wiki-bpe" /> Sennrich, Haddow and Birch adapted it in 2016 to build subword vocabularies for neural translation.<Cite id="sennrich2016" /> The training loop is short: start from single characters, count every adjacent pair across the corpus, merge the most frequent pair into a new token, and repeat until the vocabulary reaches the size you chose.<Cite id="hf-bpe" />

Take a corpus of five words with their counts: `hug` ×10, `pug` ×5, `pun` ×12, `bun` ×4 and `hugs` ×5. The starting vocabulary is the seven characters b, g, h, n, p, s, u.<Cite id="hf-bpe" />

The method generalises to unseen words because pieces like `ug` and `un` recur across many words.<Cite id="sennrich2016" /> It also shows the weakness of a character-based start: the word `mug` contains `m`, which is not in the base vocabulary, so this tokenizer would have to emit an "unknown" token.<Cite id="hf-bpe" />

<Analogy breaks="A note-taker's abbreviations stand for meaningful words; BPE merges purely by frequency, so a piece like 'ug' is common, not meaningful.">
BPE works like a student who invents shorthand while taking notes: a squiggle for a letter pair written constantly, then a squiggle for a whole common word. Rare words stay spelled out letter by letter.
</Analogy>

## Encoding and decoding

A tokenizer must be lossless: decoding the ids must give back exactly the original text, spaces and newlines included.<Cite id="minbpe" /> Decoding is the easy direction, since each id maps to a string and the strings are concatenated. Encoding repeats one rule: among the adjacent pairs in the current sequence, find the one whose merge was learned earliest, apply it, and stop when no pair has a merge.<Cite id="minbpe" /> Applying merges in learned order guarantees that encoding reproduces the same cuts that training made.

## Byte-level BPE

GPT-2 solved the unknown-character problem by starting from the 256 possible byte values instead of characters. Any text in any script, including emoji, is a sequence of bytes, so nothing is ever unknown.<Cite id="radford2019" /> GPT-2 then learned 50,000 merges on top of the bytes and added one special end-of-text token, for a vocabulary of 50,257.<Cite id="radford2019" /> It also cuts text into chunks with a regular expression before merging, so that a merge never glues letters to punctuation; for example, it avoids separate tokens for "dog.", "dog!" and "dog?".<Cite id="radford2019" />

OpenAI's [tiktoken](https://github.com/openai/tiktoken) library ships these trained vocabularies with a fast encoder.<Cite id="tiktoken" /> With `pip install tiktoken`:

```python
import tiktoken
enc = tiktoken.get_encoding("gpt2")
ids = enc.encode("hello world")
print(ids)                                   # [31373, 995]
print([enc.decode([i]) for i in ids])        # ['hello', ' world']
print(enc.encode(" the"), enc.encode("the"))  # [262] [1169]
assert enc.decode(ids) == "hello world"      # lossless round trip
print(enc.n_vocab)                           # 50257
```

Two details surprise newcomers. Spaces belong to the following word, so " world" is one token. And " the" with a leading space and "the" without one are different tokens with different ids, so tokens are not words.<Cite id="tiktoken" />

## Vocabulary size is a trade-off

More merges give shorter sequences, so a context window of fixed length covers more text. But every token adds one row to the embedding table, and, unless the weights are tied, one more output score per prediction. Rare tokens are also seen rarely in training, so their rows learn slowly.<Cite id="lets-build-tokenizer" />

The code-autocompletion project measured this on Python source with embedding width 192:

| Vocabulary | Characters per token | Embedding parameters | Share of the model |
|---|---|---|---|
| 609 (512 merges) | 2.28 | 116,928 | 6% |
| 2,145 (2,048 merges) | 2.90 | 411,840 | 23% |

GPT-2's 50,257 tokens at width 256 would need about 12.9 million embedding parameters, more than three times the whole 4-million-parameter model one might train on a laptop.<Cite id="radford2019" /> Small models need small vocabularies.

<Callout type="pitfall">
Losses per token are not comparable between tokenizers. A BPE token covers several characters, so it is harder to guess than one character. Convert both to bits per character (loss ÷ characters per token ÷ ln 2) before comparing.
</Callout>

## Train the tokenizer on training data only

The merge list is learned from data, so it is part of the model. If the tokenizer is trained on the full corpus before the split, strings that occur only in the validation files can become single tokens, and validation text looks easier than truly unseen text. This is a mild but real form of [data leakage](https://en.wikipedia.org/wiki/Leakage_(machine_learning)): information from the evaluation data reaching the model during training.<Cite id="wiki-leakage" /> The rule is the same as for normalisation statistics: fit on the training split, then apply the frozen tokenizer to validation and test data.

## Other subword algorithms

BPE is not the only option. **WordPiece**, used by BERT, also merges pairs, but scores each pair by its frequency divided by the frequencies of its two parts, which favours pairs whose parts are rare on their own.<Cite id="hf-wordpiece" /> The **Unigram** method works in the opposite direction: it starts from a large vocabulary and repeatedly removes the tokens whose loss hurts the corpus likelihood least.<Cite id="hf-unigram" /> The SentencePiece library implements BPE and Unigram directly on raw text, treating the space as an ordinary symbol, so the same tool works for languages written without spaces.<Cite id="kudo2018" />

## Summary

- A tokenizer maps text to integer ids and back; it must be lossless.
- Characters give long sequences and words fail on unseen names; subwords balance the two.
- BPE starts from characters or bytes and repeatedly merges the most frequent adjacent pair; the ordered merge list is the tokenizer.
- Byte-level BPE (GPT-2, 50,257 tokens) can encode any string; the vocabulary size trades sequence length against embedding parameters.
- Fit the tokenizer on the training split only.
