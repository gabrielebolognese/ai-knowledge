**Data augmentation** is the practice of training on randomly altered copies of the training examples, using changes that do not alter the label: a doodle moved two pixels to the left is still an umbrella.<Cite id="d2l-aug" /> Together with dropout and batch normalization it is one of the standard tools against overfitting. This lesson adds each tool to the doodle CNN one at a time and measures what it does, first on the full training set and then on a small one where the effect is easier to see.

## Three regularisers in one sentence each

- **<Term slug="data-augmentation">Augmentation</Term>** gives the model a fresh variant of every image in every epoch, so it cannot memorise exact pixels.<Cite id="d2l-aug" />
- **<Term slug="dropout" />** sets a random half of the hidden units to zero at each training step, so no single unit can be relied on.<Cite id="srivastava2014" />
- **<Term slug="batch-normalization">Batch normalization</Term>** re-centres and re-scales each channel using the statistics of the current batch; its authors reported reaching the same accuracy with 14 times fewer training steps on their image model.<Cite id="ioffe2015" />

All three count as regularisation in the broad sense used by Goodfellow, Bengio and Courville: any change to training intended to reduce the error on new data rather than on the training data.<Cite id="goodfellow2016-reg" />

<Analogy breaks="A pupil understands the point of practising variations; the network only adjusts weights to reduce the loss on whatever images it is shown.">
Augmentation is like practising a sport under slightly different conditions every day: a new court, a bit of wind, another ball. You stop relying on one exact setting and learn the movement itself.
</Analogy>

## Augmentation for doodles

`augment.py` defines one random affine transform: rotate by up to ±10 degrees, shift by up to 8% of the width (about 2 pixels) and scale between 90% and 110%. torchvision's `RandomAffine` draws new random values every time it is called.<Cite id="tv-randomaffine" />

### Which changes keep the label

A change is safe when real inputs vary in the same way. People draw slightly off-centre, slightly tilted and at slightly different sizes, so those changes describe the test data. Large rotations do not: an upside-down tree or house never appears in the test set, and for digits a half turn changes the label outright (6 and 9). Mirroring is harmless for most of these ten classes but would be wrong for text.

## Batch normalization in a few steps

<MathSteps
  title="What BatchNorm2d does to one channel"
  legend={[
    { symbol: 'x_i', meaning: 'one value of the channel, at one position, in one image of the batch' },
    { symbol: '\\mu, \\sigma^2', meaning: 'mean and variance of that channel over the batch and all positions' },
    { symbol: '\\gamma, \\beta', meaning: 'learned scale and shift (one pair per channel)' },
    { symbol: '\\epsilon', meaning: 'a tiny constant against division by zero' },
  ]}
>
  <Step tex="\mu = \frac{1}{m}\sum_{i=1}^{m} x_i, \qquad \sigma^2 = \frac{1}{m}\sum_{i=1}^{m} (x_i - \mu)^2" words="Average the channel over every image in the batch and every pixel position, and measure its spread." />
  <Step tex="\hat{x}_i = \frac{x_i - \mu}{\sqrt{\sigma^2 + \epsilon}}" words="Shift and divide so the channel has mean 0 and variance 1 in this batch." />
  <Step tex="y_i = \hl{\gamma}\,\hat{x}_i + \hl{\beta}" words="Let the network undo the normalisation if it helps: γ and β are learned, two numbers per channel, 192 in total for 32 + 64 channels." />
  <Step tex="\text{eval: } \mu, \sigma^2 \leftarrow \text{running averages from training}" words="At test time there may be a single image, so the layer uses averages collected during training instead of batch statistics." />
</MathSteps>

This follows the definition in the original paper and the PyTorch layer.<Cite id="ioffe2015" /><Cite id="pt-bn2d" /> Because the layer behaves differently in training and evaluation, forgetting `model.eval()` before measuring gives wrong, batch-dependent results, the same trap as with dropout.<Cite id="d2l-dropout" />

## The controlled comparison

Each run below changes one thing relative to the baseline (dropout 0.5, no batch normalization, no augmentation) and keeps the rest identical: same data, same seed, five epochs, Adam at 0.001. The decision metric is validation accuracy; test accuracy is shown once per model for completeness.

Measured on the course's test machine (laptop CPU, PyTorch 2.15, seed 0), after the fifth epoch:

| Run | Change from baseline | Train acc. | Validation acc. | Gap | Test acc. | Time |
|---|---|---|---|---|---|---|
| `train.py` | none (baseline) | 94.95% | 95.75% | −0.80 | 95.67% | 4.0 min |
| `--dropout 0` | dropout off | 96.90% | 95.89% | **+1.01** | 95.67% | 3.9 min |
| `--batch-norm` | batch normalization on | 94.78% | **95.91%** | −1.13 | 95.72% | 5.1 min |
| `--augment` | augmentation on | 92.23% | 95.66% | −3.43 | 95.44% | 7.9 min |
| `--augment --batch-norm` | both | 90.88% | 95.48% | −4.60 | 95.27% | 8.7 min |

"Gap" is training minus validation accuracy, in percentage points. Three things stand out:

- **The differences are tiny.** All five validation scores lie within 0.45 points of each other. With 10,000 validation doodles, the sampling error of an accuracy near 96% is about $\sqrt{0.96 \times 0.04 / 10{,}000} \approx 0.2$ points, so differences of a few tenths are within noise.
- **Only the run without dropout overfits**, and only slightly: its training accuracy passes validation from epoch 3 and the gap reaches one point.
- **Augmentation costs time and has not paid off yet after five epochs.** Transforming every image doubles the epoch time on a CPU, and its training accuracy is lower because it is measured on the harder, transformed images. With 90,000 varied doodles and only five epochs there is little overfitting for it to cure.

### Longer training

Heavily regularised models usually learn more slowly, so five epochs may be unfair to them. Both the baseline and the combination were therefore trained for 15 epochs as well (12 and 27 minutes on the test machine):

| Run, 15 epochs | Train acc. | Best validation acc. | Gap at epoch 15 | Test acc. | Confident mistakes |
|---|---|---|---|---|---|
| baseline | 97.46% | 96.48% | **+0.98** | 96.36% | 187 |
| `--augment --batch-norm` | 93.36% | **96.78%** | −3.42 | 96.39% | **107** |

"Confident mistakes" counts wrong test answers given with more than 90% probability. The baseline's validation accuracy stops improving around epoch 8 while its training accuracy keeps rising, so its gap grows: the start of overfitting. The regularised model is still improving at epoch 15 and never overfits. On the test set the two end level (96.4%), but the regularised model is wrong with high confidence 43% less often, which matters in the drawing app. It is the model `draw_app.py` prefers when it finds it.

## A small training set makes the effect visible

To see overfitting clearly, the same comparison was repeated with only 1,200 drawings per class (900 for training, 100 for validation and 200 for test), for 15 epochs:

| Run (one change per row) | Train acc. | Validation acc. | Gap | Test acc. | Time |
|---|---|---|---|---|---|
| no dropout, no augmentation | **98.97%** | 92.80% | **+6.17** | 91.55% | 67 s |
| + dropout 0.5 | 94.99% | 93.80% | +1.19 | 91.75% | 68 s |
| + augmentation | 89.52% | **94.80%** | −5.28 | 92.90% | 134 s |
| + batch normalization | 87.99% | 93.90% | −5.91 | **93.05%** | 158 s |

Now the picture is clear. Without any regulariser the network nearly memorises its 9,000 training doodles (99% training accuracy) while validation accuracy stalls around 93% from epoch 5 on: a gap of six points, which is overfitting. Dropout shrinks the gap to about one point. Augmentation adds two more points of validation accuracy and 1.2 points on the test set, the largest gain of any single change. Batch normalization on top makes no clear difference here. The validation and test sets are small in this experiment (1,000 and 2,000 doodles), so differences under about one point are within noise.

## Try it

From `code/projects/project-doodles/`:

```bash
python augment.py                                    # outputs/augment-examples.png
python train.py --dropout 0 --tag no-dropout         # one change at a time ...
python train.py --batch-norm --tag bn
python train.py --augment --tag aug
python train.py --augment --batch-norm --tag aug-bn  # ... then the combination
python train.py --augment --batch-norm --epochs 15 --tag aug-bn-e15   # about 27 minutes
python train.py --per-class 1200 --epochs 15 --dropout 0 --tag small-plain
python train.py --per-class 1200 --epochs 15 --augment --batch-norm --tag small-aug-bn
```

Each run writes `outputs/history-<name>.json` and a curves plot, so you can lay the validation curves side by side. Keep notes of every run, including the ones that did not help.

## Summary

- Augmentation trains on randomly shifted, tilted and rescaled copies; only changes that real inputs also show are safe, and only the training set is augmented.
- Batch normalization standardises each channel per batch, then applies a learned scale and shift; in evaluation mode it uses running averages.
- Change one variable at a time, compare on the validation set, and keep the test set for the end.
- Regularisers help in proportion to the overfitting: hardly at all with 90,000 doodles and five epochs, clearly with 9,000 doodles (test 91.55% → 93.05%), and over 15 epochs they stop the gap from growing and cut the confident mistakes by 43%.
