An **autocomplete tool** turns a language model into something you can use while writing code: you give it the start of some code, and it streams a likely continuation. `complete.py` wraps the trained model in a small command-line program with three modes: a one-off prompt, an interactive session, and a watch mode that follows a file as you edit it. This lesson builds it, measures its speed, and ends with an honest comparison with production code assistants.

## Using complete.py

The tool loads a checkpoint (by default `checkpoints/char.pt`, then `bpe.pt`), rebuilds the model and tokenizer from it, and calls the sampling and stop rules from the previous lesson.

- `python complete.py --prompt "def is_even(n):"` streams one completion.
- `python complete.py` starts an interactive session: paste or type code, and an empty line asks for a completion.
- `--samples 3` shows three alternative suggestions, like an editor's suggestion list, and `--temperature` and `--top-k` change how adventurous they are.
- `--watch my_script.py` checks the file twice a second and, whenever it is saved, prints a suggestion for the rest of its last line.

## Making inference fast

A suggestion is only useful if it arrives while you are still thinking. Four settings matter on a CPU:

1. **Evaluation mode.** `model.eval()` switches off dropout, so outputs are deterministic for a fixed seed.
2. **No gradients.** `generate` runs under `torch.no_grad()`, which stops PyTorch from recording operations for backpropagation, saving memory and time.<Cite id="pt-no-grad" />
3. **Threads.** `torch.set_num_threads` sets how many CPU threads PyTorch uses within an operation.<Cite id="pt-threads" /> For tiny matrices, more threads are not always faster, because coordinating them costs time.
4. **Quantization.** Storing weights as 8-bit integers instead of 32-bit floats makes the model about four times smaller, and on suitable hardware integer arithmetic is faster.<Cite id="jacob2018" />

Quantization maps each real-valued weight to one of 255 integer levels with a shared scale factor:

PyTorch's *dynamic* quantization converts the weights of every `nn.Linear` layer ahead of time and quantizes each layer's input on the fly. `complete.py --quantize` applies it with one call. The current PyTorch documentation says quantization development has moved to the separate **torchao** library and asks users of the eager-mode API to migrate to it; the call still works in PyTorch 2.15, and `complete.py` reports clearly if a future version removes it.<Cite id="pt-quantization" /><Cite id="torchao" />

## How this compares with production code assistants

The tiny model shares its core with large code models: a decoder-only Transformer, trained with next-token cross-entropy on source code, with a sub-word tokenizer and temperature sampling.<Cite id="nanogpt" /> Nearly everything else differs by orders of magnitude.

Codex is the best-documented example; according to its paper, a distinct production version of it powered GitHub Copilot. Its training set came from 54 million public GitHub repositories: 179 GB of unique Python files, filtered down to 159 GB. The largest model had 12 billion parameters. On HumanEval, 164 hand-written programming problems checked by unit tests, it solved 28.8% of problems with a single sample, and 70.2% when 100 samples were drawn per problem and any passing sample counted.<Cite id="chen2021" />

| | This project | Codex (2021) |
|---|---|---|
| Parameters | 1.8 million | up to 12 billion (about 6,600 times more) |
| Training code | 8.7 MB, one codebase | 159 GB from 54 million repositories (about 18,000 times more) |
| Context | 128 tokens (128-290 characters) | thousands of tokens (GPT-3 family) |
| Sees code after the cursor | no | yes, in later fill-in-the-middle models |
| Evaluated by | parse rate (syntax) | unit tests (correctness) |
| Hardware | a laptop CPU, under an hour | a GPU cluster |

Production assistants add techniques this project leaves out. **Fill-in-the-middle** training moves a span from the middle of each document to its end, so a left-to-right model learns to complete code *between* a prefix and a suffix, which is what happens when the cursor sits inside a function.<Cite id="bavarian2022" /> Their training data is also filtered, for example removing files that look auto-generated or have very long lines, as Codex's was.<Cite id="chen2021" />

**What the tiny model can do.** It writes code with the *texture* of Python: correct indentation, closed brackets, plausible names, `self.` inside methods, `raise ValueError(...)` and docstrings in the right places. It is a good completer of boilerplate that looks like the standard library.

**What it cannot do.** It does not understand what a function is for, it forgets anything older than its context window, it invents functions and attributes that do not exist, and it knows nothing about libraries outside the standard library. Its output should be read as a statistical continuation, not as a solution. That is also true, at a far higher level of quality, of large models: Codex's own paper reports that a single sample solved fewer than a third of its test problems.<Cite id="chen2021" />

## Where to go next

- **More and different data.** The Stack smol has 10,000 files per language for many languages. It requires a Hugging Face login and acceptance of its terms, and each file keeps its original licence.<Cite id="the-stack-smol" />
- **A bigger model on a GPU.** nanoGPT's configuration files scale the same code to GPT-2 size.<Cite id="nanogpt" />
- **Fill-in-the-middle.** Rearrange training files into prefix, suffix and middle with two special tokens, and teach `complete.py` to send the code after the cursor too.<Cite id="bavarian2022" />

## Summary

- `complete.py` streams completions from a prompt, an interactive session or a watched file, with temperature, top-k and alternative suggestions.
- `eval()`, `no_grad()`, a sensible thread count and int8 quantization are the CPU inference levers; measure each rather than assuming.
- Quantization stores weights as integers times a scale: a quarter of the memory, at the cost of small rounding errors.
- The architecture is the same as in production code models, but they are thousands of times larger, are trained on filtered data, can see code after the cursor and are tested for correctness.
- A 1.8M-parameter model completes the *form* of Python well and its *meaning* poorly; say so whenever you show it.
