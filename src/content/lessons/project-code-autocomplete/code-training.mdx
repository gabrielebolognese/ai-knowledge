**Training** the code model means showing it millions of short windows of Python and nudging its 1.8 million parameters, after every batch, towards predicting each next character better. On a laptop CPU the full run takes under an hour, and a smoke run checks the whole pipeline in a few minutes. The script, `train.py`, follows the structure of nanoGPT's training loop, with the GPU-specific parts removed.<Cite id="nanogpt" />

## Random windows of code

The encoded corpus is one long tensor of integers. Each step, `get_batch` picks random start positions and cuts out windows of `block_size` tokens; the targets are the same windows shifted one position to the right. Window position $t$ therefore learns to predict token $t+1$, and every window contributes 128 predictions at once.<Cite id="lets-build-gpt" />

<Callout type="pitfall">
Getting the shift wrong is the most common language-model bug. If `y` equals `x`, the model is asked to predict the token it is already looking at; the loss falls almost to zero and the model learns nothing useful.
</Callout>

Random windows mean there are no epochs in the usual sense. The full run takes 4,000 steps of 32 windows × 128 characters, about 16.4 million characters, so it reads the 8.7 million training characters roughly twice on average.

## Optimizer and schedule

The optimizer is **AdamW**: Adam with *decoupled* weight decay, which shrinks the weights directly instead of adding a penalty to the gradient. Loshchilov and Hutter showed that decoupling makes weight decay behave as intended with Adam.<Cite id="loshchilov2017" /> Following nanoGPT, weight decay of 0.1 applies only to matrices; biases and LayerNorm parameters are excluded, because shrinking them towards zero has no regularising benefit.<Cite id="nanogpt" /><Cite id="pt-adamw" />

The <Term slug="learning-rate" /> is not constant. It rises linearly for the first 100 steps (warm-up), because Adam's running statistics are unreliable at the start, then falls along a half cosine curve from $10^{-3}$ to $10^{-4}$. Cosine decay was popularised by Loshchilov and Hutter's SGDR paper and is the default in nanoGPT.<Cite id="loshchilov2016" />

## How long will it take?

Kaplan and colleagues observed that training a Transformer costs about six floating-point operations per parameter per training token: two for the forward pass and four for the backward pass.<Cite id="kaplan2020" /> That gives a run-time estimate before you press Enter.

The estimate is rough. Small matrices use a CPU less efficiently than large ones, other programs compete for the cores, and evaluation adds a few minutes. Treat it as an order of magnitude: this run takes tens of minutes, not seconds or days.

## Reading the loss

The loss is cross-entropy in **nats** per token, using natural logarithms. For a character model, dividing by $\ln 2$ converts it to **bits per character**, the average number of yes/no questions the model needs to guess the next character.<Cite id="wiki-entropy" /> Bits per character also allows a fair comparison with the BPE model later, whose tokens are longer than one character.

## Checkpoints and resuming

Every evaluation saves a checkpoint to `checkpoints/char.pt`. It holds the model's `state_dict`, the optimizer's `state_dict`, the step, the best validation loss, the model config and the tokenizer. PyTorch's guide recommends saving the optimizer state along with the model when you intend to resume training, because Adam's running averages are part of the training state.<Cite id="pt-save-load" />

Press Ctrl+C at any time: `train.py` catches the interrupt, saves, and `python train.py --resume` continues from the same step with the same schedule. Because the checkpoint contains the tokenizer and config, `complete.py` and `evaluate.py` need nothing else to rebuild the model.

## The smoke test

`python train.py --smoke` uses about 200 KB of code, a narrower model (0.8M parameters, 64-token windows) and 300 steps. On the test machine it finished in 1.4 minutes, with the training loss falling from 4.47 to 2.16 and the validation loss to 2.19 (3.16 bits per character). The script fails with an error if the loss does not fall by at least 0.5. If the smoke test passes, your installation, the corpus and the model code all work.

## Debugging exercise: forget the causal mask

`--no-causal-mask` switches the mask off, which recreates a classic mistake. Without the mask, position $t$ can attend to position $t+1$, which holds the very character it must predict.

## Summary

- Training draws random windows; targets are the inputs shifted by one, so each window gives T predictions.
- AdamW with decoupled weight decay, a 100-step warm-up and cosine decay from 0.001 to 0.0001 trains the model stably.
- $C \approx 6ND$ predicts the cost: about $1.8 \times 10^{14}$ FLOPs, under an hour on a laptop CPU.
- Loss starts near $\ln 97 \approx 4.57$ nats; divide by $\ln 2$ (and by characters per token) for bits per character.
- Checkpoints store model, optimizer, step, config and tokenizer; a loss that looks too good usually means the model can see the future.
