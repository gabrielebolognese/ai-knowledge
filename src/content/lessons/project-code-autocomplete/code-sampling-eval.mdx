**Sampling** turns a trained <Term slug="language-model" /> into a code completer: the model gives a probability for every possible next character, one is drawn, appended to the prompt, and the process repeats.<Cite id="hf-generate" /> How the character is drawn, and when the loop stops, matter as much as the model itself. This lesson builds both and then measures the result with a simple automatic metric: the fraction of generated function bodies that are valid Python.

## From logits to the next character

`GPT.generate` in `model.py` runs the loop used by nanoGPT.<Cite id="nanogpt" /> It crops the context to the last `block_size` tokens, because the position table has only 128 entries; runs the model; keeps only the logits of the *last* position; reshapes them with temperature and top-k; and draws one token with `torch.multinomial`, which samples an index in proportion to the given probabilities.<Cite id="pt-multinomial" /> It yields each token as soon as it is drawn, so a caller can print the completion while it is being written.

<Callout type="pitfall">
Forgetting to crop the context is a common bug: once the prompt plus completion exceeds `block_size`, the position lookup fails. Cropping also means the model simply forgets everything older than 128 characters, about three lines of code.
</Callout>

## Temperature and top-k

Always taking the single most likely character (greedy decoding) seems safest, but it makes small models loop, repeating one line again and again. Holtzman and colleagues named this failure *degeneration* and showed that pure maximisation produces bland, repetitive text even in large models.<Cite id="holtzman2019" /> Pure sampling from the full distribution has the opposite problem: now and then it picks a very unlikely character, and one wrong bracket can derail everything that follows.

Two knobs sit between those extremes. **Temperature** divides the logits before the softmax; values below 1 sharpen the distribution, values above 1 flatten it. **Top-k** keeps only the $k$ most likely characters and renormalises, which removes the long tail of unlikely choices.<Cite id="fan2018" />

For code, a low temperature works best: 0.2-0.6 with top-k between 10 and 40 suggests likely continuations without looping.<Cite id="hf-generate" /> `complete.py` defaults to temperature 0.4 and top-k 20. A related method, top-p (nucleus) sampling, keeps the smallest set of tokens whose probabilities add up to $p$, so the set grows when the model is unsure and shrinks when it is confident.<Cite id="holtzman2019" />

<Analogy breaks="A diner chooses once; the model chooses again for every single character, so small risks compound over a long completion.">
Temperature is how adventurous a regular at a restaurant is: at 0.2 they nearly always order the usual, at 1 they sometimes try something else. Top-k says they only ever look at the k dishes on the specials board.
</Analogy>

## Knowing when to stop

An editor suggestion should end where the code block ends, not run on into a new class. `complete.py` stops when any of these happens:

- **Dedent.** If the prompt ends with a block header such as `def f(x):`, the completion stops at the first non-blank line indented no deeper than that header, because the body is over.
- **Two blank lines.** PEP 8 separates top-level definitions with two blank lines, so three newlines in a row end the completion.
- **File marker.** The corpus separator `# <|file|>` means the model thinks a new file starts.
- **Token limit**, 200 by default.

While streaming, a line that so far contains only spaces is held back, because it may still turn out to be a dedent that should not be shown.

## Measuring the parse rate

Reading a few samples is essential, but it is subjective. A cheap automatic check is whether the output is *syntactically* valid Python, which the standard library's `ast.parse` decides: it either builds a syntax tree or raises `SyntaxError`.<Cite id="python-ast" />

`evaluate.py` finds every function in the **validation** files, which the model never trained on. For each one it gives the model the file's code up to and including the `def` line, lets it write the body with the stop rules above, drops an unfinished last line, and tries to parse header plus body.

## Why longer completions drift

During training, the model always sees *real* code as its context. During generation, the context is increasingly its *own* output, including any mistakes. Bengio and colleagues described this mismatch between training and inference for sequence models: errors made early change the conditions for every later prediction, and they compound.<Cite id="bengio2015" /> A misnamed variable in line 2 becomes "the" variable for the rest of the body.

The small context window makes this worse. With 128 characters of memory, the model cannot see the function signature once the body is a few lines long, so it loses track of argument names and of what the function is for. The result is code that keeps the *shape* of Python, with indentation, colons and closed brackets, while its meaning wanders.

<Callout type="warning">
Parsing is a low bar. A body can parse and still call functions that do not exist or return the wrong thing. Production code models are evaluated by running unit tests: Codex's HumanEval benchmark has 164 hand-written programming problems, each checked by tests.<Cite id="chen2021" />
</Callout>

## Summary

- Generation repeats: crop the context, take the last position's logits, apply temperature and top-k, sample, append.
- Greedy decoding loops; low-temperature sampling (about 0.4) with top-k (about 20) suits code.
- Completions stop at a dedent, two blank lines, the file marker or a token limit.
- The parse rate measures syntax on unseen functions with `ast.parse`; it says nothing about correctness.
- Long completions drift because the model conditions on its own errors and forgets anything older than its context window.
