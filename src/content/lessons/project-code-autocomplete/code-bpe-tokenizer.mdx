**Byte-pair encoding** (BPE) builds a vocabulary of frequent character sequences by repeatedly merging the most common adjacent pair of symbols into a new symbol.<Cite id="sennrich2016" /> It began as a data-compression method by Philip Gage in 1994, and Sennrich, Haddow and Birch adapted it to neural translation in 2016; it is now the standard <Term slug="tokenization" /> method for GPT-style models.<Cite id="wiki-bpe" /> This lesson writes a BPE trainer from scratch, trains the code model on its tokens, and checks whether the switch helps.

## Why go beyond characters

A character model spends capacity learning to spell. It has to predict `r`, `e`, `t`, `u`, `r`, `n` one at a time, even though `return` is a single idea. Worse, its 128-token context holds only 128 characters, about three lines, so it cannot see the function signature from the middle of a body.

Word-level tokens fix the length problem but fail on code, where identifiers such as `get_user_by_id` are endless and mostly rare. BPE sits in between: common sequences such as `self`, `return` or eight spaces of indentation become single tokens, while rare names are spelled out from smaller pieces, so there is never an unknown token.<Cite id="hf-bpe" />

## The algorithm on a toy corpus

The textbook example uses four words with their counts and an end-of-word marker `_`. Each round counts every adjacent pair, weighted by word frequency, and merges the winner everywhere.<Cite id="sennrich2016" />

The vocabulary size is a dial: base symbols plus the number of merges. GPT-2 starts from the 256 possible bytes and adds 50,000 merges and one special token, for 50,257 tokens.<Cite id="radford2019" />

<Analogy breaks="A note-taker invents abbreviations that mean something; BPE merges purely by frequency, so a piece like 'est' is just common, not a known suffix.">
BPE is like inventing shorthand while taking notes: once you have written "self." a hundred times, you give it its own squiggle, and later a squiggle for "self.name".
</Analogy>

## A BPE trainer for Python code

`tokenizer.py` follows the design of Karpathy's minbpe, an educational BPE implementation of about a hundred lines, with two adjustments for code.<Cite id="minbpe" />

**Base alphabet.** It starts from the corpus's 97 characters rather than 256 bytes. The corpus has already mapped every other character to `¤`, so bytes would only add unused symbols.

**Pre-splitting.** Like GPT-2, it first cuts text into chunks with a regular expression, and merges never cross a chunk boundary, so a merge cannot glue the end of one identifier to the start of the next.<Cite id="radford2019" /> The chunk rules are tailored to Python: a newline *together with its indentation*, an identifier with one leading space, a number, a run of punctuation, or a run of spaces. Indentation therefore becomes its own family of tokens, which suits a language where indentation is syntax.

<CodeFile path="code/projects/project-code-autocomplete/tokenizer.py" lines="44-51" title="tokenizer.py: chunks that merges never cross" />

**Speed.** A naive trainer recounts every pair in the corpus after every merge. Instead, the trainer counts each *distinct* chunk once with its frequency and keeps an index from each pair to the chunks containing it, so a merge only updates the chunks it touches. On the 8.7-million-character training split, 512 merges take about 17 seconds and 2,048 merges about a minute in pure Python.

<CodeFile path="code/projects/project-code-autocomplete/tokenizer.py" lines="70-105" highlight="87" title="tokenizer.py: the training loop" />

Encoding applies the learned merges in order of their rank inside each chunk, and caches each chunk's result, since the same identifiers recur thousands of times. For production use, OpenAI's tiktoken does the same job in Rust, several times faster, and the Hugging Face tokenizers library can also train vocabularies.<Cite id="tiktoken" />

## What the tokenizer learns

Running `python tokenizer.py --merges 512` on the training split printed these first merges:

1. two spaces, then four, then eight spaces;
2. a newline followed by eight spaces;
3. `se`, `in`, a newline followed by four spaces, `re`, `on`, `th`.

Indentation dominates because it is the most repeated text in Python. Later merges build keywords and common names: merge 200 is `raise`, merge 500 is ` key`. The line `    def __init__(self, name=None):` with its body takes 60 character tokens but 18 BPE tokens, including single tokens for ` name`, `None` and the newline-plus-indent.

On the validation files, the 512-merge vocabulary averages **2.28 characters per token** and the 2,048-merge vocabulary **2.90**. The same 128-token context therefore covers about 290 characters instead of 128, more than twice as much code.

## Vocabulary size against model size

More merges mean shorter sequences, but each extra token adds a row of 192 numbers to the embedding table, and those rows are trained only when their token appears. Rare tokens get few updates, so a small model on a small corpus cannot use a huge vocabulary well.<Cite id="lets-build-tokenizer" />

| Vocabulary | Characters per token | Embedding parameters | Share of a 1.8M model |
|---|---|---|---|
| 97 characters | 1.00 | 18,624 | 1% |
| 609 (512 merges) | 2.28 | 116,928 | 6% |
| 2,145 (2,048 merges) | 2.90 | 411,840 | 23% |
| 50,257 (GPT-2) | n/a | 9,649,344 | 530% |

This course uses 512 merges by default: a large gain in context length for a small cost in parameters. `--merges 2048` is a worthwhile experiment.

<Callout type="pitfall">
Train the tokenizer on the training files only. `train.py` calls `BPETokenizer.train(train_text, ...)`; fitting it on validation code as well would leak information about the held-out set into the vocabulary.
</Callout>

## Retraining and a fair comparison

`python train.py --tokenizer bpe` trains the tokenizer, encodes the corpus and trains a model with the same width, depth, batch size and number of steps as the character model. The model sees the same number of *tokens*, which is more *characters* of code.

Loss per token cannot be compared directly, because a BPE token is harder to guess than a single character. Both scripts therefore report **bits per character**: the loss per token divided by the characters per token and by $\ln 2$.<Cite id="hf-bpe" />

Measured on the test machine, both runs with 4 layers, 192 channels, 32 windows of 128 tokens and 4,000 steps:

| Step | Character model, validation bits/char | BPE model, validation bits/char |
|---|---|---|
| 500 | 2.56 | 2.18 |
| 1,000 | 2.17 | 1.88 |
| 2,000 | 1.88 | 1.61 |
| 3,000 | 1.70 | 1.49 |
| 4,000 | 1.65 | **1.48** |

The BPE model, with 1,921,344 parameters (98,304 more, all in the larger embedding table), is the better predictor of unseen code at every step: about 10% fewer bits per character at the end. Part of the gain is simply more data per step: 16.4 million BPE tokens cover about 37 million characters, against 16.4 million for the character model. That also shows its cost: the BPE model went through the 8.7-million-character training set more than four times, its validation loss stopped improving after step 3,500, and its gap between training and validation loss is larger. With this corpus, more BPE training would mostly mean more overfitting.

The difference is much larger when the models write code. With `python evaluate.py` on the same 100 validation functions:

| Model | Token budget per body | Bodies that parse |
|---|---|---|
| Character | 300 tokens = 300 characters | 38 / 100 |
| Character | 684 tokens = 684 characters | 46 / 100 |
| BPE | 132 tokens ≈ 300 characters | 69 / 100 |
| BPE | 300 tokens ≈ 684 characters | **81 / 100** |

Compared at the same number of characters, the BPE model's bodies parse almost twice as often. A bigger budget is not what the character model is missing: with 684 characters it still reaches only 46 / 100, and 30 of its failures are docstrings that never close. Its longer context lets it still see the function signature and the opening of a docstring when it needs to close it, and its tokens for whole keywords and indentation steps leave fewer chances to misspell structure. Its bodies are also longer, averaging 10 lines within 300 tokens. This is the trade-off that makes sub-word tokenizers the standard for language models, measured at a scale you can reproduce on a laptop.<Cite id="sennrich2016" />

## Prompt boundaries and token healing

The first test of the trained BPE model failed in an instructive way. Given `class Stack:` and `def __init__(self):` followed by a newline, all three suggestions were empty. The cause is the tokenizer, not the model. A prompt that ends with a newline is encoded with a bare newline token, but during training a newline was almost always merged with the indentation of the next line (newline plus eight spaces is one token). The model had rarely seen a bare newline followed by anything other than another blank line, so it ended the block at once.

The fix is called **token healing**: remove the prompt's last token, and constrain the first generated token to one whose text *starts with* the removed text. The model can then choose newline-plus-eight-spaces, the boundary it knows. The guidance library calls this token healing and turns it on by default for Transformer models.<Cite id="guidance-healing" /> `complete.py` does the same for BPE checkpoints; character models never need it, because every boundary between characters was seen in training.

With healing switched on, the same prompt produced ordinary suggestions such as `self._loop = loop`. Production systems handle the same problem in their own ways, but it shows a general lesson: the tokenizer is part of the model, and text boundaries the model never saw in training behave unpredictably.

## Summary

- BPE starts from characters and repeatedly merges the most frequent adjacent pair; the merge order is the tokenizer.
- Pre-splitting into chunks, with newline-plus-indentation as a chunk, keeps merges inside identifiers and gives Python's indentation its own tokens.
- 512 merges give 2.28 characters per token on unseen code, so the same context covers more than twice as much text.
- Every token costs an embedding row, so small models need small vocabularies.
- Compare models in bits per character, and train the tokenizer on training data only.
- Prompts that end at an unusual token boundary need token healing: back up one token and constrain the first new token to start with it.
